# Модель автоматизации и исключений АСД-КОНТУР v0.1

- Статус: проектная редакция для утверждения владельцем продукта
- Дата: 2026-08-19
- Владелец продукта: Олег Щербаков
- Основание: `docs/product/PRODUCT_OPERATING_MODEL_v0.1.md`;
  `docs/product/DETERMINISTIC_RULES_MODEL_v0.1.md`;
  `docs/mvp/FUNCTIONAL_MODEL_v0.1.md` §15 (полевой RAG-клиент)
- Область действия: продуктовый уровень. Не определяет конкретные модели
  OCR/VLM, форматы файлов или протоколы устройств — техническая
  реализация, отдельный артефакт.

## 1. Назначение

Детализирует раздел 3 `PRODUCT_OPERATING_MODEL_v0.1.md`: как система
получает данные, не прибегая к повторному ручному вводу, какой закрытый
перечень ситуаций всё же требует человека, и как исключение превращается
в конкретную задачу, а не в общее «на рассмотрении».

## 2. Как система минимизирует ручной ввод

Принцип **однократного цифрового происхождения**: значение вводится
человеком или извлекается системой ровно один раз, у своего источника; всё
последующее использование — ссылка на это значение, не повторный ввод
(ФМ принцип 8 «минимально необходимый ввод», без изменений). Практические
следствия:

- реквизиты, уже подтверждённые в одном документе (например, шифр
  раздела, наименование работы), не запрашиваются заново в смежном
  документе — подставляются по ссылке;
- полевая фиксация (раздел 3) использует уже опубликованную
  `RequiredDocumentMatrix`, чтобы заранее знать, что нужно зафиксировать,
  вместо того чтобы человек вспоминал состав требований;
- QR/штрихкод на партии МТР исключает повторный ручной ввод маркировки на
  каждом этапе прослеживаемости (входной контроль → выдача → применение).

Минимизация ввода не означает уменьшение проверки — правило
(`DETERMINISTIC_RULES_MODEL_v0.1.md`) проверяет каждое подставленное
значение так же, как и введённое вручную; ссылка не освобождает от
проверки применимости и происхождения.

## 3. Источники данных

| Источник | Что извлекается | Куда поступает |
|---|---|---|
| Документы (ПД/РД, регламент, НТД, договор, сметы) | реквизиты, состав требований, применимость, вид работ | `SourceCorpus`, `Requirement`, `WorkTypeRegister` |
| Фото/видео | состояние работы, место, визуальные признаки дефекта, привязка к времени и геопозиции | `Evidence` (вид `фото`) |
| QR/штрихкоды | идентификация партии МТР, сертификата, маркировки | `MaterialBatch`, `QualityDocument` |
| Журналы (производства работ, входного контроля) | хронология событий, решения входного контроля | `Work`, `IncomingControlDecision` |
| Лаборатория | результаты испытаний, методика, протокол | `Evidence` (вид `протокол_испытания`) |
| Геодезия | измерения, схема, отклонения | `Evidence` (вид `измерение`, `схема`) |

Для каждого источника действует одно и то же правило происхождения
(`DETERMINISTIC_RULES_MODEL_v0.1.md` §7) — вид источника не даёт
исключения из требования указать метод получения, версию и локатор.

## 4. Закрытый перечень исключений

Ровно три категории (`PRODUCT_OPERATING_MODEL_v0.1.md` §3.2), каждая —
закрытый список подтипов. Список не расширяется добавлением новых
подтипов без пересмотра этого документа — открытых формулировок вида
«и другие подобные случаи» не используется.

### 4.1. Категория 1 — первичный факт, которого нет в цифровом виде

1.1. Показание прибора без цифрового интерфейса (визуальный отсчёт).
1.2. Состояние конструкции при первом осмотре/обследовании
     («Восстановление», `PRODUCT_OPERATING_MODEL_v0.1.md` §4.3).
1.3. Свидетельское показание участника процесса.
1.4. Факт присутствия лица на площадке, не зафиксированный автоматическим
     средством (СКУД, геометка) на момент события.

### 4.2. Категория 2 — юридически обязательная подпись/полномочие

2.1. Подписание акта усиленной квалифицированной электронной подписью
     (вне текущего Support-среза, ФМ §3.2; точная продуктовая обязательность
     требует отдельного scope/authority решения).
2.2. Подписание договора или дополнительного соглашения.
2.3. Официальное согласование заказчиком (представитель заказчика,
     ФМ §5).
2.4. Включение объёма в КС-2/КС-3.
2.5. Приёмка работ уполномоченным лицом.

### 4.3. Категория 3 — обработка исключения

3.1. Конфликт версий одного источника (две версии, обе претендуют на
     актуальность).
3.2. Конфликт между разными типами оснований (ПД/РД против регламента
     заказчика против договора) без заданного приоритета
     (`DETERMINISTIC_RULES_MODEL_v0.1.md` §6, OD-04).
3.3. Отсутствие обязательного основания (не заведён ни один из пяти
     типов источников, необходимых для решения).
3.4. Нечитаемость (скан, фото, скан-копия — OCR/VLM не может извлечь
     значение с достаточной уверенностью).
3.5. Недостаточная определённость классификации (уверенность
     распознавания ниже порога, `DETERMINISTIC_RULES_MODEL_v0.1.md` §4,
     OD-03).
3.6. Применимость требования спорна по одному из шести измерений
     (`DOMAIN_CORE_SPEC_v0.1.md` §7.1).
3.7. Устаревшая форма/редакция без явной ссылки на переходные положения
     (`DETERMINISTIC_RULES_MODEL_v0.1.md` §3, R-APL-02) — не блокировка,
     а именно исключение, так как правило не квалифицирует это как
     ошибку автоматически.

## 5. Как исключение становится задачей

Механический, не описательный процесс — правило создания задачи такое же
детерминированное, как и правила раздела 4/6/8
`DETERMINISTIC_RULES_MODEL_v0.1.md`:

1. Правило обнаруживает, что не может дать результат (раздел 4, любой
   подтип).
2. Создаётся запись исключения (`StudyUncertainty` в общем ядре, либо
   аналогичная сущность конфликта в сценарном слое — `EvidenceConflict`,
   `RequirementConflict`, `SourceVersionConflictRecorded` —
   `docs/architecture/DOMAIN_CORE_SPEC_v0.1.md`, соответствующие агрегаты)
   с обязательными полями: причина (какой подтип раздела 4), затронутая
   сущность, правило, которое не смогло решить, и версия правила.
3. Запись немедленно превращается в адресную задачу
   (ФМ §16 «система создаёт адресные задания, а не общие уведомления» —
   без изменений, применяется к исключениям как к частному случаю):
   объект, действие, основание (ссылка на п.2), срок, приоритет,
   ответственный по роли, критерий завершения.
4. Критерий завершения задачи — всегда «предоставлен недостающий вход»
   (данные, решение о приоритете, разрешение конфликта), не «одобрено».
   Человек не одобряет чужой вывод — он поставляет то, чего не хватало.
5. После получения недостающего входа правило раздела 4
   `DETERMINISTIC_RULES_MODEL_v0.1.md` исполняется заново автоматически,
   без дополнительного шага «подтвердить, что теперь можно продолжить».

Ответственный по роли — определяется типом исключения, не общим
«ПТО»: категория 3.1–3.2, 3.6–3.7 (конфликт/применимость) — инженер ПТО
или нормативный эксперт; 3.3 (отсутствие основания) — тот, кто отвечает
за соответствующий тип источника (администратор объекта для регламента,
ПТО для ПД/РД); 3.4–3.5 (нечитаемость/уверенность) — тот, кто может
получить читаемый экземпляр или подтвердить значение вручную (обычно
исполнитель, зафиксировавший исходный файл).

## 6. Запрет на создание неподтверждённых фактов

Безусловный, не ослабляется максимальным исключением человеческого
фактора (`PRODUCT_OPERATING_MODEL_v0.1.md` §3.4) — наоборот, чем меньше
рутинных проверок человеком, тем строже это ограничение должно
соблюдаться механически, потому что не на кого рассчитывать как на
последний фильтр перед публикацией:

- **запрет на факты:** ни правило, ни ИИ-контур не создают запись
  `Evidence`/`Work`/факт о выполнении, для которой нет источника —
  отсутствие данных остаётся отсутствием данных (категория 3.3), не
  становится правдоподобным предположением;
- **запрет на подписи:** ни одна `DocumentDraft`-ревизия не может
  содержать подпись, сгенерированную системой, — регистрация подписи
  происходит только как результат категории 2 (человек подписал вне
  системы, система регистрирует факт регистрации, не сам акт подписания);
- **запрет на испытания:** результат лабораторного/геодезического
  контроля не выводится из текста проекта документа или из ожидаемого
  значения — только из зарегистрированного `Evidence` вида
  `протокол_испытания`/`измерение` (ФМ §8, без изменений);
- **запрет на даты:** дата события не подставляется «по умолчанию»
  (например, датой публикации документа) — отсутствующая дата события
  есть исключение категории 3.3/3.5, не повод использовать соседнюю
  известную дату;
- **запрет на исполнительные схемы:** геодезическая схема не
  генерируется из проектных отметок вместо фактических измерений —
  расхождение проекта и факта обязано быть видимым, не скрытым
  подстановкой проектного значения.

Это прямое применение инварианта `PRODUCT_SCOPE.md`: выдумывание фактов,
дат, подписей, испытаний или присутствия лиц запрещено во всех режимах и на
всех стадиях готовности. В модели, где рутинная человеческая проверка
устранена, ограничение не наследуется автоматически «по умолчанию
осторожности», оно закреплено как структурное правило (раздел 4
`DETERMINISTIC_RULES_MODEL_v0.1.md`: отсутствие входа = исключение, не
пропуск шага).

## 7. Пример прослеживания одного поля (синтетический, не пилотные данные)

Иллюстрация модели, не реальный кейс — помечено явно, чтобы не быть
принятым за фактический пилотный сценарий (блокировано D-02):

1. Фото партии арматуры с читаемым QR на бирке загружено прорабом с
   планшета (offline, синхронизировано позже).
2. Правило распознаёт QR → сопоставляет с `MaterialBatch`, уже
   зарегистрированной при поставке. Уверенность высокая → автоматически:
   `ApplicationRecord` создаётся, партия помечена «применена».
3. Другое фото — бирка частично оторвана, QR нечитаем. Уверенность
   ниже порога → категория 3.4. Создаётся задача: «подтвердите номер
   партии для фото [ссылка], читаемый QR не найден» — адресована
   прорабу, зафиксировавшему исходное фото (не абстрактному «ПТО»).
4. Ни на одном из двух шагов не создаётся окно «проверьте, правильно ли
   система распознала партию» для успешного случая (п.2) — только
   неуспешный случай (п.3) порождает задачу.

## 8. Открытые решения (специфичные для этого документа)

- **OD-05** — закрытый перечень раздела 4 составлен на основе уже
  известных документов (ФМ, PRODUCT_SCOPE); при появлении пилотных
  данных (D-02) возможны дополнительные подтипы категории 3, специфичные
  для конкретного объекта — потребуется явное расширение этого документа,
  не тихое добавление в коде.
- **OD-06** — правило распределения ответственного по роли (раздел 5,
  последний абзац) — рабочая гипотеза, не согласованная отдельно с
  моделью доступа ФМ §6; требует сверки при детализации ролей (открытое
  решение D-04 функциональной модели, организационная модель
  использования).
