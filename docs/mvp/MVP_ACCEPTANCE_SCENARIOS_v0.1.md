# Сквозные приёмочные сценарии АСД-КОНТУР v0.1

- Статус: проектная редакция для утверждения владельцем продукта
- Дата: 2026-08-19
- Владелец продукта: Олег Щербаков
- Основание: `docs/mvp/FUNCTIONAL_MODEL_v0.1.md` §10, §19 (AC-01…AC-16);
  `docs/product/PRODUCT_OPERATING_MODEL_v0.1.md`;
  `docs/product/DETERMINISTIC_RULES_MODEL_v0.1.md`;
  `docs/product/AUTOMATION_AND_EXCEPTIONS_v0.1.md`;
  `docs/architecture/DOMAIN_CORE_SPEC_v0.1.md`
- Область действия: продуктовый уровень, сценарии для приёмки. Не
  содержит тестового кода, фикстур или конкретных пилотных данных —
  реальное наполнение блокировано D-02 (пилотный ОКС и технологическая
  цепочка, `docs/mvp/FUNCTIONAL_MODEL_v0.1.md` §22).

По ADR-0007 этот каталог является частичной исторической выборкой сценариев,
а не достаточной приёмкой продукта. Готовность требует отдельных E2E suites
и terminal conditions для `Tender`, `Support`, `Audit`, `Restoration`;
отсутствующий здесь Tender-сценарий является пробелом каталога, а не режимом
за границей готовности.

## 0. Как читать сценарии

Каждый сценарий описан единообразно: **Дано** (предусловия) → **Шаги**
(с пометкой автоматически/исключение/категория 1–2 —
`docs/product/PRODUCT_OPERATING_MODEL_v0.1.md` §3.2) → **Результат** →
**Критерий приёмки** (ссылка на существующий AC-* ФМ, где применимо, или
новый AC-S* для сценариев, не покрытых существующими критериями). Ни
один сценарий не описывает человека, «проверяющего вывод системы» как
рутинный шаг — только три категории участия, определённые в
`docs/product/PRODUCT_OPERATING_MODEL_v0.1.md` §3.2.

## 1. Изучение ОКС и формирование матрицы

**Дано:** `SourceCorpus` собран (ПД/РД, регламент ИД заказчика, НТД,
договор — все четыре типа, `docs/architecture/DOMAIN_CORE_SPEC_v0.1.md`
§5.1); структура ОКС заведена администратором объекта (вне объёма
изучения).

**Шаги:**

1. Запуск `StartStudyOfConstructionObject` — автоматически, как только
   `SourceCorpus` содержит все обязательные типы оснований.
2. Извлечение и классификация сведений — автоматически (ИИ-контур как
   поставщик кандидатов, `PRODUCT_OPERATING_MODEL_v0.1.md` §3.1).
3. Публикация `WorkTypeEntry` для каждого однозначно распознанного вида
   работ — автоматически (R-WT-01,
   `docs/product/DETERMINISTIC_RULES_MODEL_v0.1.md` §4).
4. Вычисление `RequirementApplicability` по каждому виду работ —
   автоматически (R-APL-01).
5. Публикация `RequiredDocumentMatrixEntry` — автоматически (R-MTX-01).
6. Работа, для которой распознавание неоднозначно (конкурирующие
   кандидаты, применимость спорна) — **исключение**, категория 3.5/3.6
   (`docs/product/AUTOMATION_AND_EXCEPTIONS_v0.1.md` §4.3), создаётся
   адресная задача инженеру ПТО.
7. Завершение `StudyOfConstructionObject` — автоматически, если нет
   открытых блокирующих исключений (`docs/architecture/DOMAIN_CORE_SPEC_v0.1.md`
   §5.2, инвариант 1).

**Результат:** опубликованные `WorkTypeRegister` и
`RequiredDocumentMatrix` для ОКС, с объяснением каждой записи (правило,
версия, источник, локатор — `DETERMINISTIC_RULES_MODEL_v0.1.md` §7);
список неразрешённых исключений, если есть.

**Критерий приёмки:** новый **AC-S1** — «100% распознанных видов работ
имеют либо подтверждённую запись матрицы, либо явное исключение с
причиной; ни одна работа не остаётся без записи молча». Опирается на
AC-02 (происхождение) без изменений.

## 2. Аудит комплекта ИД и выдача дельты

**Дано:** опубликованная `RequiredDocumentMatrix`; существующий
фактический корпус `Evidence`/`DocumentDraft` для уже выполненных работ
(режим обязателен для готовности продукта; сценарий описывает целевое
поведение, ещё не подтверждённое реализацией,
`docs/product/PRODUCT_OPERATING_MODEL_v0.1.md`
§4.2).

**Шаги:**

1. Сопоставление каждой записи матрицы с фактическим корпусом —
   автоматически.
2. Классификация расхождения (отсутствует / неприемлемо / противоречиво)
   — автоматически, по правилам полноты и совместимости версий
   (`DETERMINISTIC_RULES_MODEL_v0.1.md` §6).
3. Сомнение в подлинности уже имеющегося документа (например, признаки
   несоответствия хеша заявленному содержимому) — **исключение**,
   категория 3.1/3.4.
4. Формирование отчёта о дельте — автоматически, с объяснением каждой
   позиции.

**Результат:** отчёт «требуется по матрице, но отсутствует/неприемлемо»
с точной ссылкой на правило и основание для каждой позиции.

**Критерий приёмки:** новый **AC-S2** — «отчёт о дельте не содержит
позиций без ссылки на конкретную запись матрицы и конкретную причину
расхождения». Критерий обязателен для E2E-готовности режима «Аудит»; его
успех не может быть выведен из проверки Support-среза.

## 3. Восстановление проекта недостающего документа только из подтверждённых данных

**Дано:** `RequiredDocumentMatrixEntry`, для которой отсутствует
документ; доступны источники восстановления иного происхождения —
архивные сканы, натурные измерения, свидетельские показания
(`docs/product/PRODUCT_OPERATING_MODEL_v0.1.md` §4.3).

**Шаги:**

1. Свидетельское показание или натурное измерение вносится человеком —
   **категория 1** (первичный факт, которого нет в цифровом виде), не
   исключение и не рутинная проверка.
2. Регистрация внесённого факта как `Evidence` с происхождением
   (кто, когда, каким методом получено) — автоматически, как только
   факт внесён.
3. Верификация `Evidence` (`EvidenceVerification`) — автоматически, если
   формальные признаки подтверждения присутствуют (например, натурное
   измерение сопровождается зафиксированным прибором и методом).
4. Сборка `DocumentDraft` из подтверждённых `Evidence` — автоматически.
5. Позиция матрицы, для которой ни один источник восстановления не даёт
   подтверждённого доказательства, — **не заполняется предположением**;
   остаётся `ЗАБЛОКИРОВАН` либо переводится в `Deficit` со статусом
   «признан неустранимым» решением уполномоченного лица (это решение —
   категория 2/3, не рутинная генерация).
6. Попытка сформировать `DocumentDraft` без подтверждённого
   `RequiredEvidenceSet` — отклоняется структурно (отказ команды
   `MarkDraftReadyForSignature`, `docs/architecture/DOMAIN_CORE_SPEC_v0.1.md`
   §16.3), не создаёт черновик с пустыми полями «для заполнения позже».

**Результат:** `DocumentDraft`, каждое поле которого прослеживается до
подтверждённого источника; либо явно признанный неустранимым дефицит —
никогда «правдоподобный» документ без источника.

**Критерий приёмки:** **AC-10** (ФМ, «проект пилотного комплекта
сформирован только из подтверждённых данных») — распространяется на
режим «Восстановление» без изменения формулировки; дополнительно новый
**AC-S3** — «ни один `DocumentDraft` в режиме „Восстановление“ не
содержит поля без ссылки на `Evidence`, зарегистрированный после начала
восстановления».

## 4. Сопровождение одной технологической цепочки

**Дано:** пилотная технологическая цепочка (D-02, не подставлена реальными
данными); `RequiredDocumentMatrix` опубликована для входящих в неё видов
работ.

**Шаги:**

1. Прораб фиксирует начало работы, применённую партию МТР, фото/
   измерения — обычный производственный ввод (не категория 1: это
   плановая фиксация факта в момент его возникновения, предусмотренная
   процессом, а не первичный факт, «появившийся» вне цифрового контура).
2. Проверка допуска партии МТР (входной контроль) — автоматически, если
   решение входного контроля уже зарегистрировано.
3. Формирование состава обязательных доказательств для контрольной точки
   — автоматически, из `RequiredDocumentMatrixEntry`.
4. Закрытие контрольной точки — автоматически, если все обязательные
   доказательства подтверждены (R-CPL-01).
5. Отрицательный результат контроля — **не исключение** (правило точно
   знает, что произошло) — создаётся `Defect`, статус `ЗАБЛОКИРОВАН`, не
   задача «разберитесь, что случилось».
6. Сборка `DocumentDraft` (АОСР) — автоматически, из подтверждённых
   доказательств.
7. Подписание АОСР уполномоченным лицом — **категория 2**.

**Результат:** доведённый до `ГОТОВ К ВЫПУСКУ` проект АОСР; статус
`VolumeReadiness` для объёма пересчитан.

**Критерий приёмки:** AC-06 (МТР), AC-08 (контрольная точка), AC-09
(отрицательный контроль), AC-13 (готовность) — без изменений; новый
**AC-S4** — «ни один шаг 1–6 не создаёт задачу человеку вне трёх
категорий раздела 0».

## 5. Блокировка документа при недостающем доказательстве

**Дано:** `RequiredDocumentMatrixEntry`, для которой предусмотрено
обязательное доказательство (например, протокол испытания); доказательство
ещё не зарегистрировано.

**Шаги:**

1. Попытка перевести `DocumentDraft` в статус «готов к подписанию» —
   автоматически отклоняется правилом полноты (R-CPL-01).
2. Статус документа — `ЗАБЛОКИРОВАН`, причина — точная ссылка на
   отсутствующую запись (`DETERMINISTIC_RULES_MODEL_v0.1.md` §8.2), не
   общее «не готово».
3. Это состояние **не создаёт задачу в очереди исключений** — путь
   устранения известен (получить недостающее доказательство обычным
   ходом процесса), система не спрашивает человека, что делать.
4. Регистрация недостающего доказательства (обычный ввод, не категория 1,
   если доказательство уже существует в другой системе/журнале и просто
   вносится) — снятие блокировки автоматически при следующей проверке
   полноты.

**Результат:** документ остаётся видимо заблокированным до появления
доказательства; не публикуется частично готовым, не помечается ложно
готовым.

**Критерий приёмки:** AC-08 (ФМ) без изменений; новый **AC-S5** —
«заблокированный документ никогда не переходит в `ГОТОВ К ВЫПУСКУ` без
прохождения правила полноты повторно, независимо от того, кто и как
внёс недостающее доказательство».

## 6. Сценарий неучтённого объёма для будущего сметного модуля

**Явно иллюстративный сценарий**, зависящий от нереализованного модуля
(интеграция smetter.ru, `docs/product/PRODUCT_OPERATING_MODEL_v0.1.md`
§7) — не входит в текущую приёмку Support-среза и приведён только чтобы
граница общего ядра и будущего модуля была явной уже сейчас. Это не выводит
применимые Tender/Audit capabilities за границу готовности продукта.

**Дано (гипотетически):** `RequiredDocumentMatrix` и фактические объёмы
работ (`WorkVolume`) опубликованы; внешний API smetter.ru возвращает
актуальные сметные нормативы.

**Шаги (гипотетически):**

1. Сопоставление фактического объёма с нормативным расходом по сметным
   нормам — кандидат от внешнего адаптера (`External Estimation
   Boundary`, `TECHNICAL_ARCHITECTURE_v0.1.md` §11), не публикуется
   напрямую (то же правило «кандидат/решение», что и для внутреннего
   ИИ-контура).
2. Расхождение сверх допустимого — **исключение**, не автоматическая
   корректировка сметы: система не решает вместо сметчика, что делать с
   неучтённым объёмом, она точно указывает, где объём разошёлся с
   нормативом и на основании какого источника.

**Результат (гипотетически):** список позиций неучтённого объёма с
объяснением по формату раздела 7 `DETERMINISTIC_RULES_MODEL_v0.1.md`.

**Критерий приёмки:** не определяется в этой редакции; это явный пробел
будущей четырёхрежимной acceptance suite, а не исключение из продукта.
Сценарий приведён как проверка непротиворечивости границы (раздел 10
`TECHNICAL_ARCHITECTURE_v0.1.md`) до его реализации.

## 8. Открытые решения (специфичные для этого документа)

- **OD-07** — новые критерии AC-S1, AC-S4, AC-S5 не проходили процедуру
  утверждения, применённую к AC-01…AC-16 в `FUNCTIONAL_MODEL_v0.1.md`
  §19 — требуют формального включения в реестр критериев при следующей
  ревизии функциональной модели (связано с OD-01,
  `docs/product/PRODUCT_OPERATING_MODEL_v0.1.md` §9).
- **OD-08** — `Superseded` ADR-0007 в части границы готовности: Audit и
  Restoration обязательны вместе с Tender и Support. Порядок внутренней
  реализации может быть поэтапным, но не меняет product readiness gate.
