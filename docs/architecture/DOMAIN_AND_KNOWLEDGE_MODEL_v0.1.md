### 1.1. Список и ответственность

| **Audit and Lifecycle** | Неизменяемый журнал решений/действий (платформенных и workspace); состояния `Workspace` от инициализации до сброса | Контур D (журнал) + §5 Blueprint |

### 1.3. Запрещённые зависимости (жёсткое ограничение)

1. **Retrieval Indexes и Typed Knowledge Graph не могут быть источником
   истины ни для одного другого контекста** — Canonical Knowledge Model,
   Deterministic Rules и Workspace/ОКС не читают решения из индекса/графа
   напрямую, только через Knowledge Tool Gateway, и то — как кандидата
   (EvidencePack), не как факт.
2. **Canonical Knowledge Model и Deterministic Rules не зависят от
   Workspace/ОКС.** Платформенный слой не содержит ссылок на конкретный
   `workspace_id` в определении сущности (кроме `RuleEvidence`/
   `PromotionCandidate`, которые *ссылаются* на исходный workspace как на
   происхождение уже промотированного знания — раздел 3.5, не наоборот).
3. **Knowledge Tool Gateway не имеет прав записи ни в один канонический или
   правиловый контекст** — тот же принцип, что уже зафиксирован для
   AI-контура в `TECHNICAL_ARCHITECTURE_v0.2.md` §7 («отказ или
   недоступность контура OCR/извлечения не останавливает Rules Engine»),
   распространён на весь Knowledge Tool Gateway.
4. **LLM/VLM не имеет прямого доступа к PostgreSQL** — единственный путь
   чтения знаний — типизированные инструменты Gateway; единственный путь
   записи — предложение кандидата через `ExtractionRecord`/
   `PromotionCandidate`, никогда прямая публикация факта или правила
   (`KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §9, первый пункт).
5. **Promotion Gate — единственный путь из workspace-памяти в платформенную
   память.** Ни Workspace/ОКС, ни Deterministic Rules, ни ручная миграция
   в обход состояний Gate (раздел 3.5) не создают платформенную запись.

### 2.1. Source & Evidence Ledger

#### `SourceArtifact`

- **Назначение.** Логическая идентичность принятого первоисточника,
  независимая от его редакций, мест хранения и производных представлений.
- **Область.** Контекстно-зависима: `platform`, если артефакт — НТД
  (`SourceType = НТД`); `workspace`, если артефакт — ПД/РД, регламент ИД
  заказчика, договор, утверждённый перечень ИД, либо любой факт ОКС.
  Определяется полем `owning_scope`, не отдельным типом сущности.
- **Идентификатор.** `source_artifact_id` (UUID). Natural identifier, URL и
  digest не являются primary key или capability.
- **Обязательные поля.** Точный состав G-01 обязан вывести из контракта:
  `source_artifact_id`, owning scope, owner/organization/workspace reference,
  source kind и created provenance; storage path в identity не входит.
- **Версионирование.** Сама identity стабильна; каждая новая редакция или
  повторно полученное содержимое создаёт immutable `SourceVersion`.
- **Связи.** Один `SourceArtifact` владеет одной или несколькими
  `SourceVersion`; каждая версия ссылается на scoped object metadata и exact
  object version receipt, определяемые G-01/G-03.
- **Инварианты.** Версия и bytes не переписываются; физическая
  cross-workspace deduplication project blobs запрещена, хотя логический
  digest может совпадать.
- **Provenance.** Получение конкретного содержимого фиксирует
  `SourceVersion.acquisition_provenance`
  (`DOMAIN_CORE_SPEC_v0.1.md` §5.1, `AcquisitionProvenance`).
- **Судьба при archive/reset ОКС.** Workspace identity, версии и bytes
  следуют одному ownership/deletion plan: archive содержит разрешённые
  immutable versions и object receipts; reset удаляет project content по
  `RetentionProfile`. Платформенные НТД не подлежат workspace reset.

#### `SourceVersion`, `SourceLocator`, `SourceType`

Не вводятся заново — полностью определены `DOMAIN_CORE_SPEC_v0.1.md`
§3.1, §5.1, §5.6 и реализованы в `src/asd_kontur/domain/sources.py`. Этот
документ добавляет одно поле к `SourceVersion` (расширение, не замена):
`source_artifact_id → SourceArtifact.source_artifact_id` — связь версии с
логической identity источника. Физическое object metadata и receipts
определяются G-01/G-03 без введения второго значения термина.

### 2.2. Normative Documents (специализация Canonical Knowledge Model)

#### `NormativeDocument`, `NormativeEdition`

Не вводятся заново — уже реализованы `src/asd_kontur/ntd/models.py`
(идентичность документа отделена от датированной редакции, `supersedes`
— явная цепочка замещения, `OfficialSource`/`RetrievalAttempt` — уже
формализованное происхождение). Область — всегда `platform`. Этот
документ фиксирует то, что код уже реализовал, как часть формальной
модели, и добавляет связь с новым уровнем — `StructuralUnit` (ниже):
`StructuralUnit.edition_id → NormativeEdition.id`, которой в коде пока
нет (раздел 3.9 — что отсутствует).

#### `StructuralUnit`

- **Назначение.** Один структурный узел внутри конкретной редакции
  документа — раздел, пункт, подпункт, приложение, таблица, рисунок.
  Дословный текст без интерпретации — граница с `KnowledgeAssertion`
  (семантика) обязательна и не размывается.
- **Идентификатор.** `structural_unit_id` (UUID); дополнительно
  уникальный составной ключ `(edition_id, clause_ref)` — предотвращает
  дублирование пункта внутри одной редакции (аналог
  `uq_normative_clause` из `mac_asd/src/db/models.py:710`, но привязан к
  `edition_id`, а не к текстовому `doc_code`, — устраняет риск смешения
  редакций одного документа, обнаруженный там же).
- **Область.** `platform`.
- **Обязательные поля.** `edition_id → NormativeEdition.id`,
  `unit_kind` (раздел | пункт | подпункт | приложение | таблица |
  рисунок), `clause_ref` (человекочитаемый номер, «п.3.5»), `text`
  (дословно), `page_number`, `parent_unit_id` (иерархия, nullable для
  корневых разделов).
- **Версионирование.** Неизменяем после публикации редакции —
  исправление означает новую `NormativeEdition`, не `UPDATE` существующей
  `StructuralUnit` (тот же принцип неизменяемости истории, что
  `ADR-0003`).
- **Связи.** `KnowledgeAssertion.anchor_unit_id → StructuralUnit.id`
  (один узел может быть основанием для нескольких утверждений);
  `CrossReference` (раздел 2.6) — рёбра между узлами, в том числе разных
  редакций/документов.
- **Инварианты.** `clause_ref` уникален внутри `edition_id`; `text` не
  может быть пустым для узлов видов `пункт`/`подпункт` (пустой текст —
  явный признак сбоя структурного разбора, не валидный узел — раздел 5).
- **Provenance.** `edition_id` + `page_number` — уже достаточный локатор;
  дополнительно `extraction_method` (`native_text` | `ocr` | `vlm` |
  `manual`) — тот же принцип разделения методов, что уже принят для
  workspace-извлечения (`docs/architecture/TM35_OCR_AND_VLM_EXTRACTION_POLICY_v0.1.md`),
  распространённый на платформенный конвейер НТД.
- **Судьба при archive/reset.** Не применимо — платформенная сущность,
  не привязана ни к одному workspace, сброс ОКС её не затрагивает.

### 2.3. Canonical Knowledge Model

#### `KnowledgeAssertion`

- **Назначение.** Единственная сущность семантически извлечённого
  знания: определение, требование, разрешение, запрет или исключение,
  привязанные к одному или нескольким `StructuralUnit`. Объединяет пять
  почти структурно идентичных сущностей списка задания (`Definition`,
  платформенное «Requirement», `Exception`, а также `permission`/
  `prohibition` из `KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §3.2) —
  обоснование объединения см. раздел 2.0.
- **Идентификатор.** `assertion_id` (UUID, стабилен между редакциями
  ТОЛЬКО если утверждение содержательно не изменилось — правило
  сопоставления между редакциями открыто, раздел 3.4.3).
- **Область.** `platform`.
- **Обязательные поля.** `kind` (`определение` | `требование` |
  `разрешение` | `запрет` | `исключение`), `anchor_unit_id →
  StructuralUnit.id` (может быть несколько через отдельную линкующую
  таблицу `assertion_anchor`, если утверждение опирается на несколько
  пунктов), `text` (нормализованная формулировка, не обязательно
  дословная — в отличие от `StructuralUnit.text`), `applicability_scope`
  (предварительная, ненормативная область применения — окончательная
  применимость к конкретному ОКС вычисляется `RequirementApplicability`
  workspace-слоя, не здесь), `effective_from`/`effective_to`
  (наследуются от `NormativeEdition`, но могут быть уже — если конкретный
  пункт введён отдельным изменением позже даты редакции в целом).
- **Версионирование.** Новая `NormativeEdition` создаёт новые
  `KnowledgeAssertion` (через новые `StructuralUnit`); связь «то же самое
  утверждение, что в прошлой редакции» — отдельное поле
  `supersedes_assertion_id`, заполняется правилом сопоставления
  (детерминированным, версионированным — раздел 3.6), не автоматически по
  совпадению текста.
- **Связи.** `anchor_unit_id → StructuralUnit`; `CrossReference` (ссылки
  на другие `KnowledgeAssertion`); `RuleEvidence.assertion_id →
  KnowledgeAssertion.id` (правило цитирует утверждение как основание).
- **Инварианты.** Не существует без `anchor_unit_id` (никогда не
  «утверждение из ниоткуда» — прямое применение запрета на
  неподтверждённые факты, `AUTOMATION_AND_EXCEPTIONS_v0.1.md` §6, к
  платформенному слою); `kind = исключение` обязан ссылаться на
  утверждение, которое он исключает (`exception_to_assertion_id`, не
  nullable для этого `kind`).
- **Provenance.** Полный `EvidenceLink` (раздел 2.8) на
  `StructuralUnit` → `NormativeEdition` → `NormativeDocument`.
- **Создание/прекращение.** Создаётся только конвейером обработки НТД
  (раздел 5 `KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md`, формализовано
  раздел 4 ниже) — кандидат до экспертного подтверждения
  (`status: кандидат → подтверждён/отклонён`, тот же паттерн, что раздел
  2.9). Никогда не создаётся напрямую из workspace-наблюдения без
  Promotion Gate.
- **Судьба при archive/reset.** Не применимо — платформенная сущность.

#### `CrossReference`

- **Назначение.** Типизированное ребро между двумя `StructuralUnit` и/или
  `KnowledgeAssertion` — ссылка, изменение, замещение, применимость,
  требование, конфликт.
- **Идентификатор.** `(from_id, to_id, edge_kind)` — составной, ребро
  одного типа между парой узлов уникально.
- **Область.** `platform`.
- **Обязательные поля.** `from_id`, `to_id` (оба — `StructuralUnit.id`
  либо `KnowledgeAssertion.id`, разграничены полем `from_kind`/`to_kind`),
  `edge_kind` (закрытый перечень: `references` | `amends` | `supersedes`
  | `applicability` | `requires` | `conflicts` | `evidence_for` — прямое
  заимствование таксономии, проверенной в `mac_asd`, раздел 4, но без
  переноса реализации), `established_by` (`структурный_разбор` |
  `правило` | `эксперт`).
- **Версионирование.** Ребро не версионируется отдельно — принадлежит
  версии узлов, которые соединяет; при новой редакции документа рёбра
  пересобираются конвейером (раздел 5), не переносятся автоматически.
- **Связи.** Прямая часть Typed Knowledge Graph (раздел 1.1) — это и есть
  строки, из которых граф проецируется, не сам граф.
- **Инварианты.** `edge_kind = conflicts` обязан иметь заполненное поле
  `conflict_description` — конфликт без описания не публикуется (тот же
  принцип «конфликт не разрешается молча», `ADR-0003` п.2).
- **Provenance.** `established_by` + (если `правило`) `rule_version_id`
  — какое именно правило построило это ребро.
- **Судьба при archive/reset.** Не применимо — платформенная сущность.

### 2.5. Platform Classifiers (справочники для применимости)

#### `WorkTypeClassifier`

- **Назначение.** Курируемый, платформенный список нормализованных видов
  работ с синонимами — НЕ то же самое, что `WorkTypeEntry`
  (workspace-scoped распознанный экземпляр, `DOMAIN_CORE_SPEC_v0.1.md`
  §5.3). Цель — дать `WorkTypeEntry` разных ОКС возможность ссылаться на
  один и тот же платформенный вид работ без повторного независимого
  распознавания «с нуля» на каждом объекте, но без создания единого
  жёсткого перечня, привязанного к номерам строк одной НТД (см. раздел
  6, урок «292 ключа классификатора, унаследованные от утратившего силу
  приказа»).
- **Идентификатор.** `work_type_classifier_id` (UUID, стабилен
  бессрочно — не пересчитывается ни при смене редакции НТД, ни при
  добавлении синонима).
- **Область.** `platform`.
- **Обязательные поля.** `canonical_label`, `synonyms` (список строк),
  `status` (`кандидат` | `подтверждён` | `устарел`), `linked_assertions`
  (какие `KnowledgeAssertion` типично применимы к этому виду работ —
  ненормативная подсказка для правил, не сама применимость).
- **Версионирование.** `canonical_label` неизменяем после подтверждения
  (переименование создаёт новую запись со ссылкой `renamed_from`, не
  переписывает историю); список синонимов — расширяемый, каждое
  добавление — отдельное событие аудита.
- **Связи.** `WorkTypeEntry.classifier_ref → WorkTypeClassifier.id`
  (nullable — распознанный, но ещё не сопоставленный с платформенным
  классификатором вид работ существует как чисто workspace-локальный
  кандидат, пока не пройдёт Promotion Gate или явное сопоставление).
- **Инварианты.** Не создаётся напрямую из одного распознавания ОКС —
  только через Promotion Gate (раздел 3.5) либо предзаполнением
  экспертом до пилота.
- **Судьба при archive/reset.** Не применимо — платформенная сущность.

#### `ConstructionElement`, `Material`, `ControlOperation`, `RequiredDocumentType`

Один и тот же шаблон, отличаются только предметной областью:

| Поле | Значение |
|---|---|
| Назначение | Платформенный, курируемый справочник (тип конструктивного элемента / материала / контрольной операции / вида обязательного документа) — измерение, по которому `Rule` (раздел 5) вычисляет применимость |
| Идентификатор | `{entity}_id` (UUID) |
| Область | `platform` |
| Обязательные поля | `canonical_label`, `synonyms`, `status` (`кандидат`\|`подтверждён`\|`устарел`) |
| Версионирование | Как `WorkTypeClassifier` |
| Связи | `RequiredDocumentMatrixEntry.RequiredDocumentKind` и `.ControlKind` (`DOMAIN_CORE_SPEC_v0.1.md` §5.5, уже существующие значения-объекты) ссылаются на `RequiredDocumentType.id`/`ControlOperation.id` соответственно, вместо свободной строки |
| Инварианты | Не создаётся напрямую из одного workspace-наблюдения — только через Promotion Gate |
| Судьба при archive/reset | Не применимо — платформенные сущности |

### 2.6. Retrieval & Graph Index Plane

#### `EmbeddingIndexVersion`

- **Назначение.** Реестр отдельных, параллельно существующих версий
  векторного индекса — формализация
  `KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §7.
- **Идентификатор.** `embedding_index_version_id` (UUID).
- **Область.** `platform` для индекса над Canonical Knowledge Model;
  дополнительно один `EmbeddingIndexVersion` на каждый активный
  `workspace_id`, индексирующий workspace-контент — оба используют один
  и тот же тип сущности, различаются полем `scope`.
- **Обязательные поля.** `embedding_model_id`, `model_revision`,
  `dimension`, `dtype`, `instruction_version`, `chunker_version`,
  `built_at`, `status` (`строится` | `активен` | `устарел` |
  `удалён`), `scope` (`platform` | `workspace`), `workspace_id`
  (обязательно при `scope = workspace`).
- **Версионирование.** Каждая новая модель/ревизия/чанкер — новая строка,
  не перезапись; переключение чтения на новую версию — отдельное
  событие (`activated_at`), старая версия не удаляется до сравнения
  (`KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §7, «Новая модель создаёт
  параллельный индекс; старый удаляется только после сравнения»).
- **Связи.** Векторные записи (не отдельная сущность каталога — строки
  индекса pgvector) ссылаются на `embedding_index_version_id` +
  `source_version_id`/`assertion_id`/`structural_unit_id`.
- **Инварианты.** Canonical Knowledge Model и `SourceVersion` не имеют
  обязательной ссылки НА `EmbeddingIndexVersion` — зависимость
  односторонняя (индекс ссылается на канон, не наоборот) — прямая
  реализация требования «канон можно сохранить при полной замене
  embedding-модели» (раздел 8 задания, критерии приёмки).
- **Судьба при archive/reset.** `scope = workspace` — индекс удаляется
  безусловно при сбросе рабочей области (он вторичен, восстановим из
  сохранённого канонического контента при необходимости, раздел 4);
  `scope = platform` — не затрагивается сбросом ни одного workspace.

#### `GraphProjectionVersion`

Тот же шаблон, что `EmbeddingIndexVersion`, с заменой embedding-полей на
`edge_kinds_included` (какие типы `CrossReference`/workspace-рёбер вошли
в эту проекцию), `projection_algorithm_version`. Формализует «граф —
производная проекция», подлежащая полной пересборке (раздел 1.3, п.1;
`KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §3.4, §11).

### 2.8. Provenance

#### `EvidenceLink`

- **Назначение.** Таблично оформленная форма уже обязательного (ADR-0003)
  происхождения — связывает ЛЮБУЮ несущую значение сущность
  (`KnowledgeAssertion`, `Rule`/`RuleVersion`, `ExtractionRecord`,
  `CrossReference`) с конкретным `SourceVersion` + локатором + методом +
  уверенностью.
- **Идентификатор.** `evidence_link_id` (UUID).
- **Область.** Наследует область владельца (`platform` для
  `KnowledgeAssertion`/`Rule`, `workspace` для `ExtractionRecord`).
- **Обязательные поля.** `subject_type` (закрытый перечень типов-
  владельцев — НЕ произвольная строка, тот же принцип, что уже отверг
  полиморфную ссылку у `DerivedCandidate`, раздел 2.0), `subject_id`,
  `source_version_id → SourceVersion.id`, `locator` (страница/пункт/
  ячейка — `SourceLocator`, `DOMAIN_CORE_SPEC_v0.1.md`), `method`
  (`native_text` | `ocr` | `vlm` | `manual` | `structural_parse` |
  `rule_execution`), `confidence` (nullable — обязателен только для
  методов `ocr`/`vlm`, отсутствует для `manual`/`structural_parse`,
  которые не имеют вероятностной природы).
- **Версионирование.** Неизменяем — исправление создаёт новую запись,
  прежняя помечается `superseded_by`.
- **Инварианты.** Каждый `subject_id` обязан иметь хотя бы одну
  `EvidenceLink`, кроме сущностей в статусе явно необоснованной
  неопределённости (`StudyUncertainty`, где сам факт отсутствия
  `EvidenceLink` и есть содержание записи).
- **Судьба при archive/reset.** Наследует судьбу владельца.

### 2.9. Общий паттерн «Candidate Lifecycle» (вместо `DerivedCandidate`)

Не отдельная сущность (раздел 2.0). Контракт, которому обязана следовать
КАЖДАЯ из следующих сущностей: `WorkTypeEntry`, `RequiredDocumentMatrixEntry`
(`DOMAIN_CORE_SPEC_v0.1.md`), `KnowledgeAssertion`, `Rule`,
`PromotionCandidate` (этот документ):

- обязательное поле `status` из закрытого перечня, минимум три значения:
  `кандидат` (создан правилом/ИИ, не опубликован), `подтверждён`
  (опубликован — детерминированным правилом автоматически либо решением
  человека, `PRODUCT_OPERATING_MODEL_v0.1.md` §3.1), `отклонён` (не
  удаляется, раздел 12 `DOMAIN_CORE_SPEC_v0.1.md`);
- обязательная ссылка на `EvidenceLink` (раздел 2.8) — без неё запись не
  может перейти в `подтверждён`;
- обязательная ссылка на правило/версию, принявшее решение
  (`rule_id`+`rule_version` либо явное «решение человека» с ролью и
  полномочием — `PRODUCT_OPERATING_MODEL_v0.1.md` §3.2);
- запрет прямого перехода `кандидат → подтверждён` в обход правила —
  структурное ограничение (раздел 12 `DOMAIN_CORE_SPEC_v0.1.md`, каталог
  отказов команд), не только регламент.

### 2.10. `AuditRecord` — расширение уже принятого `audit_log`

Не вводится заново. `TECHNICAL_ARCHITECTURE_v0.2.md` §6.1 уже определяет
`audit_log` как append-only, `INSERT`-only на уровне прав роли приложения.
Этот документ добавляет одно структурное требование, отсутствовавшее в
исходном определении: **`workspace_id` — обязательное поле, nullable
только для действий без workspace-контекста** (продвижение знания через
Promotion Gate, курирование платформенного классификатора, построение
`CrossReference` конвейером НТД). Действие, единственный субъект которого
— workspace-сущность, обязано иметь заполненный `workspace_id` без
исключений — прямая техническая основа для проверки отсутствия утечки
после сброса (раздел 4.4).

## 3. Workspace и жизненный цикл

### 3.1. `Workspace`

- **Назначение.** Изолированная рабочая область одного lifecycle-цикла
  обработки одного ОКС. По IA-OD-02/C она содержит один или несколько
  governed `ModeExecution` (`Tender`, `Support`, `Audit`, `Restoration`),
  но не разделяет данные с другим workspace неявно.
- **Идентификатор.** `workspace_id` (UUID) — единственный обязательный
  дискриминатор изоляции (раздел 4).
- **Область.** По определению — сама единица workspace-области; не имеет
  внешнего "workspace_id", кроме собственного.
- **Обязательные поля.** `workspace_id`, `oks_ref` (внешняя, непрозрачная
  для платформы бизнес-идентичность ОКС — не первичный ключ платформы,
  так как один и тот же ОКС может иметь несколько `Workspace` за время
  жизни), `lifecycle_state` (раздел 3.2), `organization_id`, `created_at`,
  `created_by`. Режим принадлежит `ModeExecution`, не `Workspace`; legacy
  `workspace.mode` мигрирует в первый ModeExecution.
- **Версионирование.** `Workspace` сам не версионируется — версионируются
  его дочерние сущности (`SourceCorpus`/`StudyOfConstructionObject` уже
  версионируются ревизиями, `DOMAIN_CORE_SPEC_v0.1.md` §5.1–5.2).
  Повторный независимый engagement того же `oks_ref` создаёт НОВЫЙ
  `Workspace` с новым `workspace_id`. По IA-OD-03/B данные прежнего цикла
  могут попасть только через authorized verified archive import с новыми
  версиями, ownership и lineage; прямое наследование/чтение запрещено.
- **Связи.** Владеет (через `workspace_id`) ВСЕМИ workspace-scoped
  таблицами без исключения (раздел 4.1) — `SourceCorpus`,
  `StudyOfConstructionObject`, `WorkTypeRegister`, `Requirement`,
  `RequiredDocumentMatrix`, весь сценарный слой «Сопровождение»
  (`DOMAIN_CORE_SPEC_v0.1.md` §5.7–5.14), локальные `EmbeddingIndexVersion`/
  `GraphProjectionVersion`, `ExtractionRecord`, `ModeExecution`.
- **Инварианты.** Ровно один `lifecycle_state` в любой момент (раздел
  3.2); переход состояний — только вперёд, без пропуска состояний
  (раздел 3.2 диаграмма), кроме аварийного перехода в «Архив» из любого
  состояния (раздел 3.2, исключение).
- **Provenance.** `created_by` + событие аудита `WorkspaceInitialized`.
- **Судьба.** Сама является единицей archive/reset — не «судьба
  сущности внутри workspace», а предмет раздела 3.2.

### 3.2. `WorkspaceLifecycle` — пять состояний

Формализация `ARCHITECTURE_BLUEPRINT_v0.1.md` §5 на уровне переходов,
разрешённых команд и инвариантов между состояниями:

```text
Инициализация ──▶ Активная обработка ──▶ Контролируемое закрытие ──▶ Архив/хранение ──▶ Сброс рабочей области
      │                    │                        │
      └────────────────────┴────────────────────────┴──▶ (аварийный переход) Архив/хранение
```

| Состояние | Вход (условие) | Разрешено | Запрещено | Выход |
|---|---|---|---|---|
| **Инициализация** | `CreateWorkspace` с `oks_ref`, `organization_id`, profiles; затем `CreateModeExecution` | Загрузка `SourceArtifact`/`SourceVersion`, настройка профиля правил (`RuleSetVersion` — раздел 5.4), назначение доступа и mode contracts | `StartStudyOfConstructionObject` — обязательное условие выхода — минимум один `SourceCorpusEntry` каждого требуемого `SourceType`, либо явная `StudyUncertainty` о его отсутствии (`DOMAIN_CORE_SPEC_v0.1.md` §5.1, инвариант 3) | Команда `ActivateWorkspace`; запуск каждого ModeExecution отдельно проверяет его inputs/authorities/RuleSet |
| **Активная обработка** | из «Инициализация» | `StartStudyOfConstructionObject`, `RerunStudyOfConstructionObject`, все команды сценарного слоя (`DOMAIN_CORE_SPEC_v0.1.md` §8.4–8.11), синхронизация полевого клиента | Экспорт финальной версии, продвижение через Promotion Gate (Gate требует «Контролируемое закрытие» минимум, раздел 3.5) | Команда `RequestWorkspaceClosure` |
| **Контролируемое закрытие** | из «Активная обработка» | Завершение открытых `StudyUncertainty`/исключений, финальная сборка выходов, **запуск Promotion Gate** (раздел 3.5) — единственное состояние, из которого Gate разрешён | Новые полевые факты, новая загрузка источников (структурное ограничение — не регламент) | `CompleteWorkspaceClosure` — требует нулевого числа блокирующих `StudyUncertainty` (тот же инвариант, что `StudyOfConstructionObject` §5.2, распространён на уровень `Workspace`) |
| **Архив/хранение** | из «Контролируемое закрытие» ИЛИ аварийно из любого состояния | Регламентированное чтение, экспорт (раздел 4.3) | Любая запись, кроме событий аудита о самом архивировании | `InitiateWorkspaceReset` — не автоматически, отдельная команда с отдельным подтверждением (тот же принцип «dry-run + подтверждение», что уже проверен как правильная часть `mac_asd/src/core/project_lifecycle.py`, раздел 6) |
| **Сброс рабочей области** | из «Архив/хранение» | Purge workspace-scoped project content по `RetentionProfile` и deletion plan; сохранение только content-free audit/attestation; верификация отсутствия утечки (раздел 4.4) | Ничего — терминальное состояние `Workspace` | — (терминально) |

**Отклонение от `ARCHITECTURE_BLUEPRINT_v0.1.md` §5, требующее явного
обоснования:** Blueprint формулирует пять состояний как таблицу
назначений, не как строгий автомат с запрещёнными переходами. Этот
документ добавляет: (а) запрет пропуска состояний, кроме аварийного пути
в «Архив»; (б) обязательное условие выхода из «Контролируемое закрытие»
(ноль блокирующих `StudyUncertainty`) — прямая проекция уже принятого
инварианта `StudyOfConstructionObject` (`DOMAIN_CORE_SPEC_v0.1.md` §5.2)
на уровень `Workspace`; (в) явную привязку Promotion Gate ровно к одному
состоянию. Не противоречие, а обязательное уточнение для того, чтобы
переходы были детерминированными командами, не описательными
состояниями.

## 4. Канон и производные данные — hard isolation

### 4.1. Технические механизмы изоляции

Ни один из механизмов ниже не заменяет остальные — уровни складываются:

1. **Обязательный `workspace_id`.** Каждая workspace-scoped таблица
   (полный список — раздел 3.1, «связи» + весь сценарный слой
   `DOMAIN_CORE_SPEC_v0.1.md` §5.7–5.14) обязана иметь колонку
   `workspace_id UUID NOT NULL REFERENCES workspace(workspace_id)` — без
   исключений, включая таблицы очередей (`arq`/Redis задачи несут
   `workspace_id` в теле задачи), индексы (raise раздел 4.2) и
   `audit_log` (раздел 2.10).
2. **Схемное разделение платформы и рабочих областей — два уровня, не
   один.** Модернизация схемы `mac_asd` (`tooling`/`experience`/
   `object_data`/`smeta` — 4 схемы, растущие по категориям данных,
   раздел 6): здесь ровно ДВЕ схемы верхнего уровня —
   `platform` (все платформенные таблицы разделов 2.1–2.7) и
   `workspace` (все workspace-scoped таблицы, различаемые ВНУТРИ схемы
   по `workspace_id`, не по отдельной схеме на каждый ОКС — количество
   ОКС не ограничивает количество схем PostgreSQL). Схема — грубая,
   структурная граница (роль сброса физически не имеет прав DDL/DML на
   `platform`); `workspace_id`+RLS (следующий пункт) — тонкая граница
   внутри `workspace`.
3. **PostgreSQL Row-Level Security на каждой таблице схемы `workspace`.**
   Политика `USING (workspace_id = current_setting('app.workspace_id')::uuid)`
   — приложение обязано установить `app.workspace_id` в начале каждой
   транзакции; отсутствие установки не даёт доступ к «всем» строкам, а не
   даёт доступ ни к одной (`DEFAULT DENY`, не `DEFAULT ALLOW`). RLS — не
   замена проверке в Application-слое, а вторая, независимая от кода
   граница: ошибка в коде запроса (пропущенный `WHERE workspace_id = …`)
   не приводит к утечке, потому что СУБД физически не вернёт чужие
   строки.
4. **Композитные внешние ключи с `workspace_id`.** Там, где таблица
   ссылается на другую workspace-scoped таблицу (например,
   `RequiredDocumentMatrixEntry.work_type_ref → WorkTypeEntry.id`), внешний
   ключ обязан быть составным: `(workspace_id, work_type_ref) REFERENCES
   work_type_entry(workspace_id, id)` — структурно исключает случайную
   ссылку на запись из чужого `workspace_id` даже при коллизии UUID
   (теоретическая, но не бесплатная защита — соответствует требованию
   задания «составные ключи»).
5. **Репозиторный guard в Application-слое.** Каждый репозиторий
   workspace-scoped агрегата обязан принимать `workspace_id` как
   обязательный, не опциональный первый параметр конструктора — тот же
   принцип, что уже описан для домена (`TECHNICAL_ARCHITECTURE_v0.1.md`
   §3, порты не имеют доступа к скрытому глобальному состоянию) — метод
   репозитория без `workspace_id` в сигнатуре не существует, не «забыт».
6. **Запрет неограниченных запросов.** Ни один Query Handler (раздел 8
   `TECHNICAL_ARCHITECTURE_v0.2.md`) не имеет метода вида
   `get_all_work_type_entries()` без обязательного `workspace_id` —
   структурное ограничение интерфейса порта, не соглашение об
   использовании. Единственное легитимное «глобальное» чтение —
   платформенные справочники (раздел 2.5), у которых `workspace_id`
   отсутствует по определению области.

### 4.2. Очереди, индексы, рёбра графа

- **Очереди (Redis/arq).** Тело каждой задачи обязано содержать
  `workspace_id` как поле верхнего уровня, не только внутри
  сериализованной полезной нагрузки — воркер обязан устанавливать
  `app.workspace_id` (пункт 3 выше) до выполнения любого запроса задачи,
  извлекая значение из этого поля, не из содержимого пейлоада (защита от
  ошибки сериализации, подменяющей контекст).
- **Индексы retrieval-плоскости.** `EmbeddingIndexVersion.scope = workspace`
  — векторные записи наследуют RLS через `workspace_id`, физически
  входящий в строку индекса (пункт 1); полнотекстовый индекс аналогично.
  Платформенный индекс НТД (`scope = platform`) не имеет `workspace_id`
  и физически не может участвовать в запросе, ограниченном RLS-политикой
  схемы `workspace`.
- **Рёбра графа.** `CrossReference` (платформенные, раздел 2.3) не имеют
  `workspace_id`. Workspace-scoped рёбра (например, «эта `WorkTypeEntry`
  подтверждает эту `RequiredDocumentMatrixEntry`») — отдельная таблица в
  схеме `workspace`, тот же составной ключ, что и остальные workspace-
  таблицы. Единая физическая таблица «все рёбра всех типов» не
  используется — типизация на уровне схемы, не на уровне общего
  `edge_kind`-столбца с потенциально смешанными областями.

### 4.3. Retention — принятые решения и нормативная ссылка

Единственное нормативное место принятия и полных формулировок RD —
`LIFECYCLE_AND_RETENTION_SPECIFICATION_v0.1.md` §19. Решением владельца
продукта Олега Щербакова от 2026-08-21 все пять RD имеют статус `Accepted`:

- **RD-01, вариант B.** Каждый промышленный workspace ссылается на полный
  versioned `RetentionProfile`; отсутствие значения для класса данных
  блокирует finalize, purge и destroy. Сроки являются policy data с provenance,
  а WAL/backups/snapshots — residues до истечения своего срока.
- **RD-02, вариант C.** Portable logical archive является доказательным
  product archive; physical backup/PITR — независимый recovery-контур и не
  заменяет его.
- **RD-03, вариант A.** После verified reset сохраняются только content-free
  audit и `DestructionAttestation`; project content или подробные
  псевдонимизированные факты не сохраняются. Обобщённое знание проходит
  завершённый Promotion Gate до purge.
- **RD-04, вариант C.** Необратимые PURGE/DESTROY требуют versioned Basis
  Registry, evidence, полного deletion plan, legal-hold check и независимых
  полномочий запроса/подтверждения; частичный сбой не бывает `verified`.
- **RD-05, вариант B.** Approved promoted knowledge сохраняет только
  минимальный Evidence Capsule по allowlist Lifecycle Specification §10.2;
  live-link и project memory исходного workspace уничтожаются.

Эти краткие следствия не переопределяют нормативный текст Decision Cards.
Календарные сроки и basis codes не выдумываются доменной моделью: они
утверждаются как версии соответствующих policy registry.

### 4.4. Проверка отсутствия утечки после сброса

Не декларация, а исполняемая, документированная процедура:

1. **Структурная проверка.** `SELECT count(*) FROM information_schema.columns
   WHERE table_schema = 'workspace' AND column_name = 'workspace_id'` —
   обязано совпадать с числом таблиц схемы `workspace` минус явно
   задокументированные исключения (список исключений — пустой по
   умолчанию, любое добавление — отдельное архитектурное решение,
   не тихая правка).
2. **Проверка нулевых строк по конкретному `workspace_id`.** После
   `InitiateWorkspaceReset` — по каждой таблице схемы `workspace` (тот
   же список, что и в пункте 1) выполняется `SELECT count(*) ... WHERE
   workspace_id = :reset_id`, ожидаемый результат — 0 для всех project-content
   таблиц. Принятый RD-03 разрешает вне operational workspace только
   content-free audit и `DestructionAttestation`; portable archive и recovery
   residues учитываются отдельными adapters. Список ожидаемых нулей и
   допустимых content-free записей сравнивается автоматически, не проверяется на
   глаз — прямое устранение дефекта, обнаруженного в `mac_asd`
   (`project_lifecycle.py`, раздел 6): там подсчёт «удалённых строк»
   существует, но пост-фактум проверки «остались ли строки» — нет
   вообще, а перехват `except Exception` в `_clear_registry`/
   `_clear_consumption` превращает сбой удаления в тихий «удалено 0»,
   неотличимый от «удалять было нечего».
3. **Проверка индексов и графа.** `EmbeddingIndexVersion`/
   `GraphProjectionVersion` со `scope = workspace` и данным
   `workspace_id` обязаны быть в статусе `удалён` — не «помечены на
   удаление», а физически отсутствовать в файловой/векторной структуре
   (векторный индекс pgvector — часть той же таблицы схемы `workspace`,
   удаляется тем же механизмом, что и остальные строки; отдельного
   индекса, переживающего удаление строк, не создаётся).
4. **Проверка blob-store.** Project `SourceArtifact` принадлежит одному scope;
   после удаления последней разрешённой scoped reference его operational copy
   подлежит удалению по зафиксированному plan. Portable archive и recovery
   residues — отдельные copies/adapters и живут до срока своего
   `RetentionProfile`; platform artifact не участвует в workspace plan.

## 5. Реестр правил (Deterministic Rule Registry)

Архитектурная детализация lifecycle, scope, `RuleSetVersion`, conflict policy,
evaluation и trace выполнена в
`DETERMINISTIC_RULES_CATALOGUE_v0.1.md`. Настоящий раздел сохраняет
канонические identities и связи; при расхождении детального rule contract
применяется Catalogue. Владелец продукта 2026-08-21 принял `DR-01/B…DR-04/B`:
разрешены только формальные строго scoped Workspace RuleVersion, controlled
RuleSet upgrade, class-qualified approval с независимым reviewer и
subject-specific ConflictPolicy с human fallback.

### 5.1. `Rule`

- **Назначение.** Стабильная идентичность одного детерминированного
  правила независимо от версии его реализации — соответствует уже
  описанным в прозе `DETERMINISTIC_RULES_MODEL_v0.1.md` (`R-SRC-01`,
  `R-APL-01`, `R-WT-01`, `R-MTX-01` и т.д.), формализованным здесь как
  данные, не как документ.
- **Идентификатор.** `(scope, workspace_id?, rule_key)`; `rule_key` —
  человекочитаемый стабильный ключ,
  например `R-MTX-01` — тот же формат, что уже используется в прозе,
  не меняется. Для `platform` `workspace_id = null`, для `workspace` он
  обязателен и входит во все ссылки/ключи изоляции.
- **Область.** `platform` либо строго `workspace` по `DR-04/B`.
- **Обязательные поля.** `rule_key`, `title`, `group` (полнота |
  применимость | распознавание | матрица | последовательность | сроки |
  полномочия | совместимость версий), `current_version_id →
  RuleVersion.id`.
- **Версионирование.** `Rule` — только идентичность; фактическое
  поведение — у `RuleVersion` (ниже). Смена `current_version_id` — само
  по себе событие аудита, не тихое обновление указателя.
- **Судьба при archive/reset.** Platform Rule сохраняется. Workspace Rule
  входит в archive package и уничтожается вместе с workspace по
  RetentionProfile; её возможное продвижение создаёт новую обезличенную
  platform Rule через Promotion Gate, а не сохраняет исходную запись.

### 5.2. `RuleVersion`

- **Назначение.** Одна конкретная, неизменяемая, тестируемая реализация
  правила.
- **Идентификатор.** `(scope, workspace_id?, rule_key, version)` — составной,
  `version` монотонно возрастает в пределах scoped identity.
- **Область.** `platform` либо строго `workspace`; во втором случае обязательны
  `workspace_id`, exact pinned RuleSet inclusion и hard isolation.
- **Обязательные поля.**
  - `applicability_predicate` — формальное условие, когда версия правила
    применяется (например, диапазон дат `RuleSetVersion`,
    `DOMAIN_CORE_SPEC_v0.1.md` §5.2);
  - `typed_inputs` / `typed_outputs` — схема входа/выхода (тип, не
    вольный текст) — например, `R-APL-01`: вход — `Requirement` +
    шесть измерений применимости (`DOMAIN_CORE_SPEC_v0.1.md` §5.4),
    выход — `RequirementApplicability` со статусом из закрытого перечня;
  - `priority` — значение только внутри именованной conflict group и
    утверждённой versioned subject-specific `ConflictPolicy` при пересечении с
    другой `RuleVersion` той же группы (`DR-03/B`); универсальная глобальная
    иерархия и last-write-wins запрещены;
  - `effective_from`/`effective_to` — период, когда эта версия
    ДЕЙСТВУЕТ как правило системы (не путать с `EffectivePeriod`
    источника, на который правило ссылается — это разные интервалы);
  - `test_suite_ref` — ссылка на набор позитивных/негативных/граничных
    тестов (раздел 5.3);
  - `status` (`drafted` | `evidence_attached` | `candidate` | `reviewed` |
    `approved` | `active` | `suspended` | `superseded` | `retired` |
    `rejected`); полный переходный контракт определён в
    `DETERMINISTIC_RULES_CATALOGUE_v0.1.md` §4;
  - `author`, `reviewed_by`, `reviewed_at`, `approved_by`,
    `approver_authority_ref`, `approved_at` (nullable до соответствующих
    переходов); reviewer и approver — независимые human identities, approver
    имеет действующую class-qualified authority (`DR-02/B`).
- **Версионирование.** Сама сущность и есть версия — неизменяема после
  `status = approved`; любое изменение поведения — новая строка с новым
  `version`.
- **Связи.** `RuleEvidence.rule_version_id → RuleVersion` (раздел 5.3);
  каждое решение `Candidate Lifecycle` (раздел 2.9) ссылается на
  конкретную `(rule_key, version)`, не только на `rule_key` —
  воспроизводимость обязана указывать точную версию, исполнившую
  правило, не «правило вообще» (тот же принцип, что уже в
  `DOMAIN_CORE_SPEC_v0.1.md` §13 для `RuleSetVersion`).
- **Инварианты.** `status = approved` невозможен без непустого
  `test_suite_ref`, содержащего минимум один позитивный, один
  отрицательный и один граничный тест (раздел 5.3) — правило без тестов
  структурно не может быть утверждено, не только по регламенту.
  Переход `candidate → approved` не может исполнить сама модель,
  предложившая правило (нет самоутверждения — раздел 5.4).
  Workspace RuleVersion не может быть создана или утверждена LLM, службой или
  очередью; free-form override запрещён. Она не может отменить обязательную
  норму более высокой применимой authority, молча изменить platform
  RuleVersion или стать доступной другому workspace (`DR-04/B`).
- **Provenance.** `RuleEvidence` (ниже) — на чём основано само правило
  (какие пункты НТД/договора/регламента оно реализует), не с чем оно
  работает во время исполнения (это `EvidenceLink` конкретного
  решения, раздел 2.8).
- **Судьба при archive/reset.** Platform RuleVersion сохраняется; workspace
  RuleVersion подчинена archive/reset/purge данного workspace и не переживает
  reset без нового platform record, прошедшего Promotion Gate.

### 5.3. `RuleEvidence`

- **Назначение.** Основание САМОГО правила — какие `KnowledgeAssertion`
  (или, до полного разбора канона, `StructuralUnit`) правило
  реализует. Отдельно от `test_suite_ref` — тесты проверяют поведение,
  `RuleEvidence` — обосновывает право правила на существование.
- **Идентификатор.** `(rule_version_id, assertion_id)` — составной.
- **Область.** Owning record совпадает с `RuleVersion`: `platform` либо тот же
  обязательный `workspace_id`. Workspace RuleEvidence может ссылаться на
  разрешённый immutable platform source/assertion и evidence своего workspace,
  но никогда на evidence другого workspace; такая platform-ссылка не меняет
  scope и retention owning workspace record.
- **Обязательные поля.** `rule_version_id`, `assertion_id →
  KnowledgeAssertion.id` (или `structural_unit_id`, если правило
  реализует требование до его семантического разбора — переходное
  состояние, не постоянное), `relationship` (`реализует` | `противоречит`
  — второе значение фиксирует уже известный конфликт между правилом и
  текстом). Неразрешённое `противоречит` создаёт `RuleConflict` и блокирует
  активацию/включение версии в промышленный RuleSet; видимость конфликта не
  является его разрешением.
- **Инварианты.** `RuleVersion.status = approved` требует минимум одной
  `RuleEvidence` с `relationship = реализует` — недекларативное правило
  без ссылки на текст не проходит утверждение (структурное продолжение
  требования `ADR-0003`, применённое к правилам, не только к выводам).
- **Судьба при archive/reset.** Совпадает с судьбой owning RuleVersion;
  workspace evidence уничтожается по RetentionProfile и не переносится в
  platform audit.

### 5.4. Прохождение утверждения — кто утверждает `RuleVersion`

Не автоматически детерминированным правилом более высокого уровня (иначе
бесконечная рекурсия ответственности) и не моделью, предложившей
правило-кандидат: переход `reviewed → approved` — исключительно действие
class-qualified уполномоченного человека (категория 2/3
`PRODUCT_OPERATING_MODEL_v0.1.md`
§3.2 — правило само по себе не «юридическая подпись», но governance
детерминированного ядра — граница, которую задание прямо запрещает
переносить на модель или на повторяемость). Переход `candidate →
reviewed` требует независимого reviewer authority. Автоматическое прохождение
`test_suite_ref` может создать только технический статус `review_ready`, но не
заменяет review и не утверждает содержание. Reviewer — другая human identity,
не author; approver имеет действующую authority точного `rule_class`. Product
Owner управляет системой полномочий, но не обязан утверждать каждую
RuleVersion. Изменение evidence, predicate, output contract, effective
interval или conflict policy создаёт новую RuleVersion и новый review cycle
(`DR-02/B`).

Каждый workspace получает pinned `RuleSetVersion` при создании. Controlled
upgrade по `DR-01/B` не меняет этот pin до полного успешного завершения impact
preview, compatibility checks, authority approval, versioned recomputation и
integrity verification. Прежние RuleEvaluation, RuleTrace и deliverable
versions неизменяемы. `archived`, `reset` и `destroyed` workspace не
обновляются; rolling rules запрещены.

### 5.5. Как реестр поддерживает цепочку «вид работ → МТР → контроль → документы → ИД → предъявление → КС → оплата»

Каждое звено цепочки — уже специфицированный агрегат/переход
(`DOMAIN_CORE_SPEC_v0.1.md`, `PRODUCT_OPERATING_MODEL_v0.1.md` §5), этот
реестр — единственный производитель перехода между звеньями:

| Звено цепочки | `RuleVersion` (группа) | Вход | Выход |
|---|---|---|---|
| вид работ | `распознавание` (`R-WT-01`) | `ExtractionRecord` (раздел 2.1... уже §2.1) + `WorkTypeClassifier` | `WorkTypeEntry` (кандидат → подтверждён) |
| МТР | (сценарный слой, вне общего ядра — `DOMAIN_CORE_SPEC_v0.1.md` §5.8) | `WorkTypeEntry` подтверждён | допуск `MaterialBatch` |
| контроль | `применимость`+`полнота` (`R-APL-01`, `R-CPL-01`) | `RequiredDocumentMatrixEntry` + факт контроля | `ControlEvent`/`Defect`/`Deficit` |
| обязательные документы | `матрица` (`R-MTX-01`) | подтверждённый `WorkTypeEntry` + `Requirement` | `RequiredDocumentMatrixEntry` |
| ИД | (сценарный слой) | `RequiredDocumentMatrixEntry` подтверждена | `DocumentDraft` |
| предъявление объёмов | `полнота`+`последовательность` (`R-CPL-01`, `R-SEQ-01`) | `DocumentDraft`, `ControlPoint` | `VolumeReadiness` |
| КС | вне общего ядра — категория 2 (юридическое действие человека) | `VolumeReadiness = ГОТОВ К ВЫПУСКУ` | включение в КС-2/КС-3 (только человеком) |
| оплата | вне продукта (бухгалтерский учёт, `PRODUCT_SCOPE.md` «Не входит») | — | — |

Реестр не producing новое звено цепочки — он лишь формализует уже
принятые в `DOMAIN_CORE_SPEC_v0.1.md`/`DETERMINISTIC_RULES_MODEL_v0.1.md`
переходы как версионируемые записи с тестами, а не только как текстовое
описание.

## 6. Knowledge Tool Gateway — контракты

### 6.1. Общий контракт `EvidencePack`

Расширение минимального `Result{}` из `ARCHITECTURE_BLUEPRINT_v0.1.md`
§7 до полной формы, требуемой заданием:

```json
{
  "evidence_pack_id": "uuid",
  "workspace_id": "uuid | null",
  "query": { "tool": "knowledge.search", "arguments": { "...": "..." } },
  "results": [
    {
      "assertion_id": "uuid | null",
      "structural_unit_id": "uuid | null",
      "quote": "дословная цитата",
      "document": { "designation": "СП 70.13330.2012", "edition_id": "uuid", "edition_label": "..." },
      "locator": { "clause_ref": "п.3.5", "page_number": 42 },
      "applicability": { "effective_from": "2012-...", "effective_to": null, "scope_note": "..." },
      "retrieval_score": { "lexical": 0.0, "dense": 0.0, "rrf": 0.0, "rerank": 0.0 },
      "rule_trace": [ { "rule_key": "R-APL-01", "version": 3 } ]
    }
  ],
  "gaps": [ { "reason": "недостаточная_определённость", "description": "..." } ],
  "conflicts": [ { "left": "assertion_id_1", "right": "assertion_id_2", "description": "..." } ],
  "produced_at": "iso8601"
}
```

`gaps`/`conflicts` — обязательные поля, не опциональные: пустой массив —
явное «пробелов не найдено», отсутствие поля — структурная ошибка
контракта (прямое устранение слабости `mac_asd`, раздел 6: «graceful
degradation, никогда исключения» без явного различения «пусто, потому что
нечего найти» и «пусто, потому что сервис недоступен» — здесь второе
всегда отдельное поле `error`, не тихий пустой `results`).

### 6.2. Инструменты

| Инструмент | Вход | Выход | Workspace scope | Фильтры | Ошибки/uncertainty |
|---|---|---|---|---|---|
| `knowledge.search` | `query_text`, `kind` (опционально: `определение`\|`требование`\|…), `as_of_date` (опционально) | `EvidencePack` (много результатов, ранжированы) | Опционален — если передан `workspace_id`, дополнительно ищет по workspace-контенту (ПД/РД, регламент, договор этого ОКС), не только по платформенному канону | дата применимости, редакция, `kind`, `workspace_id` | `gaps: [{reason: "нет_совпадений"}]` при пустом результате — не ошибка |

| `knowledge.explain_conflict` | `conflict_id` (из `CrossReference.edge_kind = conflicts` либо из workspace-конфликта — `RequirementConflict`, `DOMAIN_CORE_SPEC_v0.1.md` §5.4) | `EvidencePack.conflicts[0]` развёрнуто — обе стороны конфликта с их `EvidenceLink`, статус разрешения | Опционален | — | `error`, если конфликт уже разрешён и запрошен как открытый (несовпадение ожидания вызывающей стороны — явная ошибка, не молчаливый актуальный статус) |

### 6.3. Что Gateway структурно не может сделать

Продолжение раздела 1.3: ни один инструмент не имеет параметра,
позволяющего передать произвольный SQL/фильтр вне заранее определённой
схемы аргументов (защита от «typed tool, использованного как прокси для
SQL-инъекции через параметр фильтра» — тот же принцип, что уже
сформулирован для API `TECHNICAL_ARCHITECTURE_v0.2.md` §8: «без прямого
доступа роутов к репозиториям в обход команд», распространённый на
инструменты LLM). Ни один инструмент не возвращает данные ДРУГОГО
`workspace_id`, чем переданный (или платформенные данные, если
`workspace_id` не передан и инструмент это допускает, раздел 6.2,
столбец «Workspace scope») — проверяется тем же RLS-механизмом (раздел
4.1, п.3), не отдельной логикой на уровне инструмента (структурная, не
regламентная защита).

Не миграции и не ORM (по прямому ограничению задания) — соответствие
уже описанных сущностей физическим механизмам:

| `AuditRecord`/`audit_log` | Authoritative PostgreSQL MBP, append-only logical contract; content-minimal node copies допускаются только по policy (`TECHNICAL_ARCHITECTURE_v0.2.md` §6.1) | ADR-0008 не меняет audit semantics, только physical authority |

Локальный профиль MBP M5 Max 128 GB / 2 TB учтён (`KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md`

привязывает ни одну сущность домена к MLX/Apple Silicon/конкретной
модели: `ExtractionRecord.method` (раздел 8) — открытый, закрытый
перечень методов, ни один из которых не именует конкретный движок,

типа).

## 8. `ExtractionRecord` — формализация уже существующего кода

- **Назначение.** Одна попытка извлечения/классификации workspace-
  контента AI/OCR/VLM-контуром — формализация того, что
  `src/asd_kontur/extraction/` и `src/asd_kontur/bridge/extraction_outcome.py`
  уже реализуют как `TextLayerEvidence` | `VlmCandidateEvidence` |
  `VlmClassification` | `VlmFailure` (union-тип `ExtractionOutcome`).
- **Идентификатор.** `extraction_record_id` (UUID); код сейчас
  идентифицирует запись по `relative_path` (ключ словаря результатов) —
  раздел 9 отмечает это как то, что должно измениться при переходе к
  персистентности.
- **Область.** `workspace`.
- **Обязательные поля (union по `outcome_kind`).**
  `outcome_kind` (`pdf_text_layer` | `vlm_candidate_evidence` |
  `vlm_classification` [устаревший, обратная совместимость] |
  `failure`), `source_version_id`, `page`, `method`, `model_reference`
  (nullable для `pdf_text_layer`), `confidence` (nullable для
  `pdf_text_layer` — детерминированный метод не имеет вероятностной
  природы), `raw_payload` (JSON — уже есть в коде как `work_type_evidence`/
  `text`), `status` (`Candidate Lifecycle`, раздел 2.9).
- **Версионирование.** Неизменяем после записи; повторный прогон над той
  же страницей создаёт новую `ExtractionRecord`, не переписывает
  прежнюю — уже реализовано в коде (`load_extraction_results`,
  «последняя запись побеждает» при построении ТЕКУЩЕЙ проекции, но
  исходный список не мутируется).
- **Связи.** `WorkTypeEntry.derived_from → ExtractionRecord.id` (через
  `bridge.build_candidates_from_extraction`, уже реализовано);
  `EvidenceLink` на `ExtractionRecord` как на источник конкретного
  `WorkTypeEntry`-кандидата.
- **Инварианты.** `outcome_kind = failure` не может иметь
  `work_type_evidence`/`text` — уже гарантировано типами кода
  (`VlmFailure` — отдельный класс, не запись с пустыми полями);
  `outcome_kind = vlm_candidate_evidence` с
  `requires_ocr_or_manual_review = true` блокирует построение
  `WorkTypeEntry` независимо от прочих полей — уже реализовано
  (`bridge/build.py`, `build_candidates_from_extraction`).
- **Provenance.** `EvidenceLink` с `method` = значению
  `ExtractionRecord.method` — не дублирование, а прямая проекция уже
  собираемых в коде полей (`source_sha256`, `image_sha256`, `page`,
  `model_path`, `prompt_version`) в формальную схему.
- **Судьба при archive/reset.** Удаляется при сбросе workspace вместе с
  прочим workspace-контентом; сохраняется в архивном снимке (раздел 4.3)
  на этапе «Архив/хранение».

## 10. Promotion Gate — состояния

Формализация принципа, уже принятого `KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md`
§4, до уровня сущностей и переходов.

### 10.1. `PromotionCandidate`

- **Назначение.** Одно предложение продвинуть конкретное workspace-
  наблюдение (подтверждённый `WorkTypeEntry`, устойчиво работающее
  сопоставление `WorkTypeMappingEntry`-аналога, зафиксированный паттерн
  ошибки) в платформенную сущность (`WorkTypeClassifier`,
  `KnowledgeAssertion`, `Rule`).
- **Идентификатор.** `promotion_candidate_id` (UUID).
- **Область.** `platform` как governance workflow, но до решения содержит
  чувствительные origin references и поэтому должна завершиться до purge.
  Unresolved `PromotionCandidate` после reset не сохраняется.
- **Обязательные поля.** `origin_workspace_id`, `origin_entity_type`+
  `origin_entity_id` (что именно предлагается продвинуть — типизированная
  ссылка, закрытый перечень типов, тот же принцип, что `EvidenceLink`
  раздел 2.8, не полиморфная свободная ссылка), `target_entity_type`
  (`WorkTypeClassifier` | `KnowledgeAssertion` | `Rule` | другой
  платформенный классификатор раздела 2.5), `state` (раздел 10.3),
  `proposed_at`, `proposed_by` (может быть системным — автоматическое
  предложение кандидата после N подтверждений допустимо, автоматическое
  ПРИНЯТИЕ — нет, раздел 10.3).
- **Версионирование.** Неизменяем после создания; повторное предложение
  того же наблюдения — новый `PromotionCandidate`, не переоткрытие
  старого (история решений не переписывается, тот же принцип, что везде
  в `DOMAIN_CORE_SPEC_v0.1.md`).
- **Связи.** `PromotionDecision` (1:1 на финальное решение, ниже).
- **Судьба при reset.** После outcome поля `origin_workspace_id`,
  `origin_entity_type` и `origin_entity_id` и весь project payload удаляются.
  Для rejected/withdrawn/expired остаётся только content-free audit outcome;
  для approved доказательная основа реплицируется только в Evidence Capsule
  по `LIFECYCLE_AND_RETENTION_SPECIFICATION_v0.1.md` §10.2.

### 10.2. `PromotionDecision`

- **Назначение.** Финальный, неизменяемый результат рассмотрения одного
  `PromotionCandidate`.
- **Идентификатор.** `promotion_decision_id` (UUID).
- **Область.** `platform`.
- **Обязательные поля до reset.** `promotion_candidate_id`, `outcome`
  (`approved` | `rejected`), `anonymization_report`,
  `applicability_definition` (для `approved` — явная область,
  где промотированное знание действует, не «везде по умолчанию»),
  `regression_test_result` (ссылка на прогон `test_suite_ref`, если
  `target_entity_type = Rule`), `decided_by`, `decided_at`.
- **Инварианты.** `outcome = approved` невозможен без непустого
  `applicability_definition` и (для правил) без `regression_test_result
  = пройден`; после `approved` создаётся (или обновляется — для
  `WorkTypeClassifier.synonyms`) целевая платформенная запись СО ССЫЛКОЙ
  на `promotion_decision_id` как на `EvidenceLink` этой платформенной
  записи — платформенное знание, возникшее из workspace-наблюдения,
  всегда трассируется до конкретного решения о продвижении, не «повисает»
  без происхождения.
- **Судьба при archive/reset исходного workspace.** По принятому RD-05,
  вариант B, approved `PromotionDecision` переживает reset только как часть
  минимального Evidence Capsule: обезличенное утверждение, тип/версия
  источника, точный locator либо разрешённый digest, применимость, сведения
  об обезличивании, проверки/regression tests, decision, identity/authority
  утвердившего, дата и период действия. `origin_workspace_id`,
  `origin_entity_id`, live-link, project document/memory/embeddings и
  unresolved AI candidates не сохраняются. Для rejected решения остаётся
  только content-free audit outcome, не capsule.

### 10.3. Состояния и переходы

```text
кандидат (PromotionCandidate.state)
   │
   ▼
обезличен ──▶ доказательства_подтверждены ──▶ применимость_определена ──▶ regression_протестирован
                                                                                   │
                                                              ┌────────────────────┼────────────────────┐
                                                              ▼                                          ▼
                                                          approved                                   rejected
                                                              │
                                                              ▼
                                                          опубликован (целевая платформенная запись создана)
```

- **кандидат → обезличен.** Автоматически допустимо (детерминированное
  правило удаления/маскирования полей из закрытого перечня — тот же
  принцип `PRODUCT_OPERATING_MODEL_v0.1.md` §3.1: если данных достаточно
  для однозначной анонимизации, правило выполняет её без человека).
- **обезличен → доказательства_подтверждены.** Требует явной проверки,
  что `EvidenceLink` исходного workspace-наблюдения (раздел 2.8)
  указывает на источник, переживающий продвижение (например, ссылку на
  НТД — платформенную сущность — а не только на факт, специфичный для
  одного ОКС). Наблюдение без переживающей продвижение доказательной
  базы не может продвинуться дальше — исключение (категория 3
  `AUTOMATION_AND_EXCEPTIONS_v0.1.md`), не блокировка с известной причиной.
- **доказательства_подтверждены → применимость_определена.** Всегда
  требует решения человека (заполнение `applicability_definition` —
  профессиональное суждение о том, где именно знание действует, не
  вычислимо детерминированным правилом из одного наблюдения).
- **применимость_определена → regression_протестирован.** Для
  `target_entity_type = Rule` — обязательный прогон `test_suite_ref`
  (раздел 5.2); для остальных типов (`WorkTypeClassifier` и другие
  справочники раздела 2.5) — эквивалент: проверка, что добавление не
  создаёт конфликтующий синоним/дубликат в уже существующем справочнике.
- **regression_протестирован → approved/rejected.** Исключительно
  решение уполномоченного человека (раздел 5.4, тот же принцип) —
  **не** высокий `confidence` исходного наблюдения, **не** число
  подтверждений, **не** ответ LLM (прямой запрет задания, раздел 3.5,
  дословно из `KNOWLEDGE_AND_MEMORY_ARCHITECTURE_v0.1.md` §4:
  «Автоматическое превращение повторившегося Lessons Learned в правило
  запрещено» — распространено на любой `target_entity_type`, не только
  на правила).
- **approved → опубликован.** Механический шаг создания/обновления
  целевой платформенной записи (раздел 10.2, инвариант) — не отдельное
  решение, прямое следствие `approved`.
