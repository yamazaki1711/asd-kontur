## 0. Как читать документ

Документ описывает **план** технической реализации, а не готовое решение.
Пункты раздела 12 («Архитектурные решения, требующие утверждения») —
рекомендации с обоснованием, а не свершившийся факт. Ничего из
перечисленного здесь не установлено захардкоженным выводом без основания:
там, где решение зависит от нормативного или продуктового факта, стоит
явная ссылка на источник или на открытое решение D-02/D-04
(раздел 12.5), которое блокирует детализацию.

### 0.1. Корректировка глобальной модели продукта

Первая редакция этого документа неявно отождествляла архитектуру
АСД-КОНТУР с архитектурой режима «Сопровождение». Это было ошибкой
масштаба, исправленной этой редакцией: **АСД-КОНТУР — комплекс
документарного обеспечения строительства**, и все четыре режима (Тендер,
Сопровождение, Аудит, Восстановление ИД) работают поверх одного общего
ядра. «Сопровождение» допускается как внутренний реализуемый сценарный
срез поверх этого ядра, но не является MVP или готовностью системы
(ADR-0007; раздел 1, раздел 9).

## 1. Общее ядро продукта и границы внутреннего Support-среза

### 1.1. Общий процесс, одинаковый для всех режимов

```text
ПД/РД + регламент ИД заказчика + применимые НТД   ← три раздельных типа оснований
        │  (раздел 4, DOMAIN_CORE_SPEC §5.2 «SourceType»)
        ▼
   Изучение ОКС (StudyOfConstructionObject)
        │
        ├─→ перечень распознанных видов работ (WorkTypeRegister)
        ├─→ применимые требования (RequirementApplicability)
        ├─→ матрица «вид работ → документ/контроль/основание» (RequiredDocumentMatrix)
        └─→ перечень неопределённостей, требующих подтверждения инженером
        │
        ▼
 ┌──────────────┬──────────────┬───────────────────┬────────────────┐
 │  Сопровождение │    Аудит     │  Восстановление ИД │     Тендер      │
 │ (Support-срез) │  (обязателен)│    (обязателен)    │  (обязателен)  │
 └──────────────┴──────────────┴───────────────────┴────────────────┘
```

Это единственный вход в систему для любого режима: ни один режим не
минует «Изучение ОКС» и не имеет собственного, отдельного способа узнать,
какие виды работ существуют на объекте и какие документы для них
обязательны. Различие между режимами — не в источнике этой информации, а
в том, что каждый режим **делает** с уже построенной матрицей (раздел 9).

### 1.2. Границы внутреннего Support-среза

Границы предметной области не переопределяются этим документом — они
зафиксированы в `docs/product/PRODUCT_SCOPE.md` и
`docs/mvp/FUNCTIONAL_MODEL_v0.1.md` §3. Уточнение масштаба после
раздела 0.1: Support-срез = общее ядро (раздел 1.1, обязательная часть)
**плюс** сценарный слой «Сопровождение» (раздел 9.1). Ядро не является
опциональной частью среза — без него нет входа в сценарий. Завершение
среза не является готовностью продукта.

Архитектурно значимое сужение:

- один подрядчик, один пилотный ОКС, один завершённый производственный
  период (ФМ §3.1) — однотенантная архитектура пилотного среза: без модели
  мультиарендности, без горизонтального шардирования по организациям;
- юридически значимый ЭДО, автоприёмка и автовключение в КС — вне текущего среза
  (ФМ §3.2) → архитектура не проектирует контур квалифицированной
  электронной подписи;
- 106 видов работ и полный охват типов ОКС — вне текущего среза (ФМ §3.2) →
  `WorkTypeRegister` архитектурно обязан быть расширяемым без миграции
  схемы (раздел 5), но сам полный справочник не строится сейчас;
- юридический анализ договоров и интеграция smetter.ru — зафиксированы
  как смежные модули (раздел 10), не реализуются в этой редакции;
- нормативная библиотека (`docs/NTD/`) — файловое хранилище договорных
  PDF, не сервис.

Выбор конкретного пилотного ОКС и технологической цепочки — открытое
решение **D-02** (раздел 12.5). До его фиксации архитектура проектируется
как применимая к любому фрагменту ОКС, без предположений о материалах,
конструктиве или объёме данных.

## 2. Локальный технологический стек без Docker

| Слой | Выбор | Статус |
|---|---|---|
| Язык и рантайм | Python 3.12, управляется `uv` (см. `docs/architecture/IMPLEMENTATION_BASELINE.md`) | зафиксировано предыдущим шагом |
| Управление зависимостями | `uv` + `pyproject.toml` + `uv.lock` | зафиксировано |
| Доменное ядро | чистый Python, без фреймворка (раздел 3) | предлагается |
| Хранилище | см. раздел 12.5, AD-01 | требует утверждения |
| Полевой клиент (offline) | отдельный процесс/приложение с локальной встроенной БД, синхронизирующийся с сервером; конкретная платформа — часть D-04 | требует утверждения |
| Сервер пилотного среза | один процесс на одной машине пилота, без оркестрации контейнеров | предлагается |
| Тестирование | `pytest` (зафиксировано baseline), `hypothesis` для property-based тестов инвариантов | предлагается |
| CI | не входит в объём этого документа; локальный `uv run pytest` — обязательный минимум до появления CI | предлагается |

**Явное ограничение «без Docker».** Причина — не техническая заповедь, а
масштаб пилота (один подрядчик, один ОКС) и offline-first требование
(полевой клиент должен работать на устройстве без доступа к
контейнер-реестру). Docker может быть пересмотрен для контура
демонстрации/CI отдельным решением, но не для полевого клиента.

## 3. Модули ядра и зависимости между ними

Архитектура внутреннего среза — слоистая (hexagonal / ports & adapters), продиктована
ADR-0001 («новое ядро не наследует ограничения MAC_ASD») и принципом
детерминированного ядра (`PRODUCT_SCOPE.md`, ФМ §4.3, §13):

```text
┌─────────────────────────────────────────────────────────────┐
│                      Adapters (внешний слой)                 │
│  Field Sync Adapter | Storage Adapter | File/Blob Adapter |   │
│  Export/Report Adapter | (перспектива) External Estimation/  │
│  Legal Adapter (раздел 10) | (позже) HTTP/API Adapter         │
└───────────────────────────┬────────────────────────────────┘
                             │ реализует Ports
┌───────────────────────────▼────────────────────────────────┐
│                       Application слой                       │
│   Command Handlers | Query Handlers | Scenario Orchestrators │
│   (Сопровождение / Аудит / Восстановление — раздел 9)        │
└───────────────────────────┬────────────────────────────────┘
                             │ вызывает
┌───────────────────────────▼────────────────────────────────┐
│              Domain Core — общее ядро (обязательное)          │
│  SourceCorpus, StudyOfConstructionObject, WorkTypeRegister,   │
│  Requirement/RequirementApplicability, RequiredDocumentMatrix,│
│  Source (полная модель — раздел 3.2)                          │
├───────────────────────────────────────────────────────────────┤
│         Domain Core — сценарный слой «Сопровождение»          │
│  Work, MaterialBatch, ControlPoint/ControlEvent, Evidence,    │
│  Defect, Deficit, DocumentDraft, VolumeReadiness               │
│  — чистые функции и инварианты, без I/O, без фреймворка        │
└───────────────────────────────────────────────────────────────┘
```

Правила зависимостей:

- Domain Core не зависит ни от одного внешнего пакета кроме стандартной
  библиотеки — прямое следствие требования детерминированности и
  воспроизводимости (`DOMAIN_CORE_SPEC_PLAN_v0.1.md` §7.4, §13);
- **сценарный слой «Сопровождение» зависит от общего ядра, но не
  наоборот** — общее ядро (`study`, `work_type_register`,
  `requirement`, `required_document_matrix`, `source`) не содержит ссылок
  на `Work`, `MaterialBatch`, `Evidence` и остальные сущности
  «Сопровождения». Это обеспечивает, что Аудит, Восстановление и Тендер
  смогут переиспользовать общее ядро, не утаскивая за собой модель
  строительного процесса, которая им не нужна (Аудит и Тендер не
  выполняют работы, они читают матрицу и сравнивают/оценивают);
- Application слой зависит от Domain Core и от портов (интерфейсов), но не
  от конкретных адаптеров;
- Adapters реализуют порты и ничего не знают о доменных инвариантах;
- ИИ-компоненты (извлечение, классификация, сопоставление, включая
  распознавание видов работ и предложение состава матрицы, раздел 5.2–5.4)
  — отдельный внешний контур, обращающийся к Domain Core только через
  Application слой как поставщик **кандидатов**, никогда как источник
  опубликованного факта (ФМ §13, PRODUCT_SCOPE «Принцип доверия»). В этой
  редакции ИИ-контур не реализуется — он спроектирован как
  заменяемый адаптер.

### 3.1. Модули общего ядра (обязательны для любого режима)

| Модуль | Агрегат(ы) | Зависит от |
|---|---|---|
| `source_corpus` | SourceCorpus | — (минимальное представление версий оснований, без полной модели `Source`) |
| `study` | StudyOfConstructionObject, StudyUncertainty | `source_corpus` |
| `work_type_register` | WorkTypeRegister | `study` |
| `requirement` | Requirement, RequirementApplicability | `source_corpus`, `work_type_register` |
| `required_document_matrix` | RequiredDocumentMatrix | `work_type_register`, `requirement` |
| `source` | Source, SourceVersion (полная модель: конфликты, замещения, отзыв) | `source_corpus` (расширяет его) |

### 3.2. Модули сценарного слоя «Сопровождение» (не входят в общее ядро)

| Модуль | Агрегат(ы) | Зависит от |
|---|---|---|
| `work` | Work, WorkRevision, WorkVolume | `work_type_register`, `requirement` (общее ядро) |
| `material_batch` | MaterialBatch, QualityDocument, IncomingControlDecision | `source` (документы качества как доказательства), `work` |
| `control_point` | ControlPoint, ControlEvent, EvidenceRequirement | `work`, `requirement`, `required_document_matrix` |
| `evidence` | Evidence, EvidenceVersion, EvidenceVerification | `control_point`, `material_batch` |
| `defect` | Defect, DefectResolution | `control_point`, `evidence` |
| `document_draft` | DocumentDraft | `evidence`, `work`, `control_point`, `required_document_matrix` |
| `readiness` | VolumeReadiness | все вышеперечисленные (только на чтение, через снимок) |

Это не структура каталогов `src/` (её создание не входит в объём задачи)
— это карта зависимостей, которой будущая структура каталогов должна
соответствовать 1:1, чтобы граница агрегата совпадала с границей модуля и
чтобы граница общего ядра совпадала с границей повторного использования
между режимами.

## 4. Типы оснований (Source Types) — раздельная модель

Три типа оснований, перечисленные в общем процессе (раздел 1.1), —
**не варианты одного и того же**, а разные `SourceType` с разными
правилами применимости, каждый со своими версиями, датой применимости,
происхождением и локаторами (полная модель — `DOMAIN_CORE_SPEC_v0.1.md`
§5.2–5.3):

| SourceType | Пример | Что определяет дату применимости |
|---|---|---|
| ПД/РД | рабочая документация раздела, чертёж, спецификация | дата выпуска редакции, дата ввода в производство работ |
| Регламент ИД заказчика | внутренний документ заказчика о составе и форме ИД | дата утверждения регламента, дата распространения на объект/договор |
| НТД | СП, ГОСТ, СНиП (`docs/NTD/`) | дата введения в действие редакции, переходные положения (раздел 8, п. про СП 543) |
| Договор *(используется общим ядром, не только перспективным юридическим модулем — раздел 10.1)* | договор подряда, дополнительное соглашение | дата вступления в силу, срок действия |
| Утверждённый перечень ИД | согласованный заказчиком состав комплекта | дата согласования |

Архитектурно все пять типов реализуются одной и той же моделью версий и
хранения (раздел 6), но **не смешиваются семантически**: применимость
требования (раздел 8) вычисляется пересечением всех применимых типов
одновременно, а не одним универсальным списком — уже зафиксированное
нормативное ограничение из предыдущей редакции, не меняется.

## 5. Storage / БД, файловое хранилище, хеширование и версии

### 5.1. Модель истины: append-only событийный журнал

Обоснование, а не предпочтение:

- ADR-0003, п.3: «каждый машинный вывод хранит ссылки… и применённое
  правило» — воспроизводимость обязана быть на уровне *истории*, а не
  только текущего состояния;
- ФМ §8: «отмена или исправление не удаляет предыдущее состояние»;
  «конфликт источников имеет отдельную запись»;
- `DOMAIN_CORE_SPEC_PLAN_v0.1.md` §13: «минимальный снимок расчёта
  готовности» — определение проекции события в конкретный момент времени;
- **(добавлено)** повторный запуск «Изучения ОКС» после изменения
  оснований (новая версия РД, новая редакция НТД) обязан создавать новую
  ревизию `StudyOfConstructionObject`, не переписывая прежнюю — те же
  инварианты неизменяемости, что и для «Сопровождения», применяются к
  общему ядру.

Источник истины — неизменяемый, только-добавляемый журнал доменных
событий; текущее состояние агрегатов и любые отчётные представления —
**проекции**, пересобираемые из журнала. Помечено AD-02 в разделе 12 —
принцип не оспаривается, но объём инженерной работы требует утверждения.

### 5.2. Физическое хранение (открытое решение — AD-01)

Без изменений от предыдущей редакции: SQLite как рекомендация для
сервера пилота и полевого клиента; критерии выбора — без Docker, без
выделенного сервера СУБД, WAL-режим, тривиальный backup копированием
файла. Переход на PostgreSQL после пилота не требует изменения
доменного ядра (порты хранения абстрагированы, раздел 3).

### 5.3. Файлы и блобы: контент-адресуемое хранилище

Без изменений: SHA-256 адресация; метаданные отдельно от блоба; путь не
несёт смысла (место/объект/работа не выводятся из пути). Применяется
одинаково ко всем `SourceType` (раздел 4) и ко всем видам `Evidence`.

### 5.4. Версии и происхождение — общая схема

Без изменений: версия неизменяема после публикации; обязательны автор,
время, метод получения, для ИИ-полей — версия модели и уверенность;
замещение — новая версия со ссылкой на предыдущую, удаления не существует.

## 6. Offline-first и идемпотентная синхронизация

Без содержательных изменений от предыдущей редакции (обязательное
свойство архитектуры, ADR-0003 п.1–2): UUID операции на устройстве,
append-only журнал клиента, идемпотентный приём по `OperationId`,
конфликт не разрешается молча, устаревшее основание не переписывает факт
задним числом. Уточнение: то же самое правило устаревшего основания
теперь явно относится не только к фактам «Сопровождения», но и к
результатам «Изучения ОКС» — устаревшая матрица требований на устройстве
не переписывает уже созданный факт, инициируется проверка влияния.

## 7. Аудит, резервирование и восстановление

Без изменений от предыдущей редакции. Резервная копия и restore drill
(раздел 6.3 предыдущей нумерации) охватывают весь событийный журнал,
включая события общего ядра (`study`, `work_type_register`,
`required_document_matrix`), не только события «Сопровождения» —
поскольку общее ядро — часть той же модели истины (раздел 5.1).

## 8. Сквозные принципы, обязательные для любой реализации

Перечислены как чек-лист — каждый пункт уже принят в другом документе:

- версия/происхождение обязательны для каждого значимого поля (ADR-0003),
  включая три раздельных типа оснований (раздел 4);
- применимость требования — пересечение ПД/РД, договора, утверждённого
  перечня ИД, объекта, технологии и даты, вычисляется на этапе
  «Изучение ОКС», не изобретается заново в каждом режиме;
- номер строки приложения А/Б СП 543 — не идентификатор вида работы;
  устойчивый `WorkTypeId` (в `WorkTypeRegister`) не совпадает и не
  зависит от номера строки конкретной редакции;
- старая форма/редакция НД не считается ошибкой автоматически без
  проверки даты введения в действие и переходных положений источника;
- ядро детерминировано; ИИ поставляет кандидатов, не решения, включая
  кандидатов видов работ и записей матрицы (раздел 5.2–5.4 плана среза);
- **(добавлено)** ни один режим не подписывает, не принимает и не
  включает объём в КС автоматически, и ни один режим не порождает
  синтетический факт вместо отсутствующего подтверждения — это
  ограничение общее для всех сценариев (раздел 9), а не специфика
  «Сопровождения»; для «Восстановления» — отдельно раздел 9.3.

## 9. Режимы как подключаемые сценарии над общей матрицей

Ни один режим не создаёт собственную копию «Изучения ОКС» — все читают
один и тот же `RequiredDocumentMatrix` для данного ОКС (с учётом его
версии/ревизии, раздел 5.1). Различие — в командах, которые режим
исполняет поверх матрицы.

### 9.1. Сопровождение (внутренний Support-срез)

Единственный режим, детализированный этой исторической редакцией до
уровня Support-среза (раздел 3.2). Это не terminal readiness режима или
продукта.
Добавляет к общему ядру исполнение работ в реальном времени: `Work`,
`MaterialBatch`, `ControlPoint`/`ControlEvent`, `Evidence`, `Defect`,
`Deficit`, `DocumentDraft`, `VolumeReadiness`. Подробности не повторяются
здесь — см. `DOMAIN_CORE_SPEC_v0.1.md`.

### 9.2. Аудит (обязательный режим; не реализован этой редакцией)

Читает `RequiredDocumentMatrix` и существующий корпус `Evidence`/
`DocumentDraft` для уже выполненных работ; вычисляет доказательную
**дельту** — что обязательно по матрице, но отсутствует или неприемлемо
фактически. Не создаёт `Work`/`MaterialBatch` — работает над уже
свершившимся. Архитектурно это read-heavy сценарий поверх тех же портов
хранения; отдельного модуля записи не требует, кроме публикации отчёта о
дельте (тип `DocumentDraft` или отдельный отчёт — решение SD-06 плана
реализации, раздел 12).

### 9.3. Восстановление ИД (обязательный режим; не реализован этой редакцией)

Тот же вход (`RequiredDocumentMatrix`), но с ключевым архитектурным
ограничением, прямо требуемым заданием: **проект документа на основе
подтверждённых сведений строго отделён от недопустимой генерации
неподтверждённых фактов.**

- допустимо: сформировать `DocumentDraft` из уже существующих
  подтверждённых `Evidence` (например, восстановленных из архивных
  сканов, журналов, свидетельских показаний, зафиксированных как
  `Evidence` со своим происхождением и проверкой) — то есть режим меняет
  **источник** доказательств (архив/обследование вместо реального
  времени стройки), но не меняет правило «доказательство обязательно и
  подтверждено» (ФМ принцип 2, `DOMAIN_CORE_SPEC_v0.1.md` §7.1);
- недопустимо: `DocumentDraft` или `Evidence`, созданные без ссылки на
  подтверждённый источник — то есть текст, дата, подпись или результат
  испытания, «правдоподобно» сгенерированные ИИ или человеком без
  основания. Это не новое правило, а прямое применение уже принятого
  инварианта PRODUCT_SCOPE (выдумывание фактов запрещено) ко всем режимам,
  не только к «Сопровождению»;
- архитектурно граница проходит там же, где для «Сопровождения»: любое
  машинное поле обязано иметь метод, версию, уверенность и исходный
  фрагмент (раздел 5.4); режим «Восстановление» не получает исключения
  из этого правила, и в этой редакции не проектируется отдельный «облегчённый»
  путь публикации `DocumentDraft` в обход `EvidenceVerification`.

### 9.4. Тендер (обязательный режим; не реализован этой редакцией)

Оценка обязательств, стоимости и рисков до заключения договора —
использует `RequiredDocumentMatrix` для оценки объёма обязательной
доказательной базы **до** начала работ. Требует данных сметного
норматива (смежный модуль, раздел 10.2) и юридического анализа договора
(раздел 10.1) — оба не спроектированы этой редакцией, поэтому её Tender-
контракт неполон и блокирует готовность; архитектурно только
зарезервировано место в разделе 3 (адаптеры) и разделе 10.

## 10. Смежные модули (зафиксированы, не реализованы этой редакцией)

Оба модуля не проектируются как адаптеры в этой исторической редакции и
фиксируются как будущие интеграционные точки. Если они необходимы для
утверждённого Tender scope, их отсутствие блокирует четырёхрежимную
готовность по ADR-0007.

### 10.1. Юридический анализ договоров и проекты протоколов разногласий

Будущая точка расширения: договор уже является одним из `SourceType`
(раздел 4) — юридический модуль добавляет собственный анализ договорных
условий (обязательства, риски, противоречия) и формирует проект
протокола разногласий как разновидность `DocumentDraft`, специфичную для
преддоговорной/договорной стадии. Не реализуется: экстрактор условий
договора, модель риска, шаблон протокола разногласий. Единственное, что
предусмотрено сейчас, — что `SourceType = Договор` (раздел 4) не потребует
переопределения при появлении этого модуля.

### 10.2. Интеграция API smetter.ru

Будущая точка расширения: внешний API для контроля материалов, смет и
оценки неучтённых объёмов по актуальным сметным нормативам. Архитектурно
это **External Estimation Adapter** — отдельный адаптер на границе
`AI Candidate Boundary`/`Export Boundary` (раздел 11), поставляющий
кандидатов оценки объёма и стоимости, не публикующий их напрямую как
факт (то же правило ИИ/человек, раздел 8). Не реализуется: клиент API
smetter.ru, сопоставление сметных норм с `WorkTypeRegister`, расчёт
неучтённых объёмов. Зафиксировано только как обязанность будущего
адаптера не иметь прямого доступа на запись к `VolumeReadiness` или
`RequiredDocumentMatrix`.

## 11. Интерфейсные границы API

Документ не проектирует конкретные эндпоинты. Границы ответственности:

| Граница | Назначение | Ключевое ограничение |
|---|---|---|
| Core Command/Query (in-process) | единственная точка входа в Domain Core | ни один адаптер не имеет прямого доступа к состоянию агрегата в обход команд |
| Field Sync Boundary | приём операций полевого клиента | идемпотентность по `OperationId` (раздел 6); никогда не выполняет профессионально значимое решение автоматически |
| Export/Report Boundary | отчёты и выгрузки (ФМ §17), включая отчёт о доказательной дельте (Аудит, раздел 9.2) | только чтение проекций; каждый экспорт фиксирует версию, дату формирования и источники; порождает событие аудита |
| AI Candidate Boundary | приём кандидатов от ИИ-контура (включая кандидатов видов работ и записей матрицы) | кандидат не публикуется как факт напрямую — обязателен командный путь через Application слой с подтверждением человеком |
| External Estimation/Legal Boundary *(перспектива, раздел 10)* | будущий приём кандидатов от smetter.ru и юридического модуля | не реализована этой редакцией; при появлении обязана соблюдать то же правило кандидат/подтверждение |

Транспорт (HTTP/REST, RPC, локальный вызов) не выбирается в этом
документе — привязан к D-08 функциональной модели и к D-04 (раздел 12.5)
в части устройства полевого клиента.

## 12. Стратегия тестирования

Без изменений в подходе от предыдущей редакции, дополнена уровнем для
общего ядра:

| Уровень | Что проверяет | Инструмент |
|---|---|---|
| Unit / инварианты | каждое правило `DOMAIN_CORE_SPEC_v0.1.md` §7 и каталог отказов §12 | `pytest` |
| Property-based | переходы состояний (включая `StudyOfConstructionObject`, `WorkTypeRegister`, `RequiredDocumentMatrix`) | `hypothesis` |
| Детерминированный реплей | одинаковый журнал событий + версия правил ⇒ побитово одинаковый `RequiredDocumentMatrix` и одинаковый `VolumeReadiness` | `pytest`, фикстуры журнала |
| Контрактные тесты портов | SQLite-адаптер и in-memory адаптер дают одинаковый результат | `pytest`, параметризация |
| Идемпотентность синхронизации | повторная отправка операции не меняет состояние второй раз | `pytest` |
| Восстановление | раздел 7, сценарий воспроизводится автоматическим тестом на синтетических данных | `pytest`, отдельный маркер |

**Явное ограничение по данным.** Тестовые фикстуры — синтетические,
маркированы как таковые в файлах фикстур, никогда не попадают в боевой
журнал событий. Реальные пилотные сценарии (ФМ §20) требуют реальных
данных пилота — блокированы D-02.

## 13. Архитектурные решения, требующие утверждения

### 13.1. AD-01 — Физическое хранилище

Без изменений: рекомендация SQLite (раздел 5.2), требует явного согласия
из-за стоимости возможной последующей миграции проекций.

### 13.2. AD-02 — Event sourcing как модель истины

Без изменений (раздел 5.1) — принцип обоснован ADR-0003 и ФМ,
утверждение нужно из-за объёма инженерной работы.

### 13.3. AD-03 — Транспорт полевой синхронизации

Без изменений — зависит от связности пилотного объекта, часть D-02.

### 13.4. AD-04 — Формат идентификаторов

Без изменений: UUID (v4) для всех `*Id`, оптимизация до ULID/UUIDv7
отложена, не блокирует реализацию.

### 13.5. AD-05 — Гранулярность SourceCorpus и StudyOfConstructionObject *(новое)*

Требует решения: являются ли `SourceCorpus` (минимальное представление
версий оснований) и `StudyOfConstructionObject` (процесс изучения)
одним агрегатом или двумя (раздел 3.1 разделяет их как два модуля с
явной зависимостью). Рекомендация — два агрегата, потому что корпус
оснований может существовать и обновляться независимо от того, запущено
ли на его основе изучение (например, при повторной публикации версии РД
до перезапуска изучения). Совпадает с SD-04 в `DOMAIN_CORE_SPEC_v0.1.md`
— решение единое для обоих документов.

### 13.6. D-02 и D-04 — пилотный ОКС и организационная модель (исправлено)

Прежняя редакция ошибочно развела «пилотный ОКС» и «технологическую
цепочку» на D-02/D-04, создав коллизию с уже принятой нумерацией
`FUNCTIONAL_MODEL_v0.1.md` §22. Исправлено по прямому указанию:

- **D-02 — Пилотный ОКС и технологическая цепочка** (единым пунктом, как
  и в `FUNCTIONAL_MODEL_v0.1.md` §22). Без этого решения архитектура не
  может установить объём данных, связность на площадке (влияет на AD-03)
  и состав документов регламента заказчика; также не может быть
  выполнено первое реальное «Изучение ОКС» на пилотных данных.
- **D-04 — Первая организационная модель использования** (как и в
  `FUNCTIONAL_MODEL_v0.1.md` §22 — без изменений смысла). Определяет, кто
  и в каком качестве работает с системой на пилоте; влияет на модель
  доступа (ФМ §6) и на выбор устройства полевого клиента (раздел 2).

Коллизии нумерации больше нет — оба пункта используют номера в точности
как в утверждённой функциональной модели.

## 14. Что документ намеренно не решает

- конкретный движок ИИ-извлечения и его версия — вне объёма;
- физическая схема таблиц проекций — производная от
  `DOMAIN_CORE_SPEC_v0.1.md` §5, отдельный артефакт после утверждения;
- пользовательский интерфейс и wireframes — отдельный артефакт (ФМ §23);
- численные SLO — открытое решение D-09 ФМ §22, зависит от пилота (D-02);
- реализация юридического модуля и интеграции smetter.ru (раздел 10) —
  зафиксированы как точки расширения, не проектируются содержательно;
- режимы «Аудит», «Восстановление» и «Тендер» — описаны как сценарии
  (раздел 9) на уровне границ, но не детализированы до команд/событий в
  этом документе; это обязательный пробел дальнейшей спецификации, а не
  перенос режимов за границу готовности продукта.
