> scope и lifecycle задаёт `LOGICAL_DATA_MODEL_v0.1.md`, а процессные

- Статус: проектная редакция для утверждения владельцем продукта
- Дата: 2026-08-19 (первая редакция); скорректировано 2026-08-19 по
  уточнённой глобальной модели продукта (раздел 0)
- Владелец продукта: Олег Щербаков
- Основание: `docs/mvp/DOMAIN_CORE_SPEC_PLAN_v0.1.md` (исторический план);
  функциональная модель режима «СОПРОВОЖДЕНИЕ» v0.1

## 0. Отличия от предыдущей редакции и от плана

### 0.1. Корректировка масштаба (эта редакция)

Предыдущая редакция начинала цепочку и порядок реализации с агрегата
`Source` и моделировала только режим «Сопровождение». Это неверно
отражало продукт: **АСД-КОНТУР — комплекс документарного обеспечения
строительства**, общее ядро для ВСЕХ режимов начинается одинаково:

`ПД/РД + регламент ИД заказчика + применимые НТД → изучение ОКС → перечень видов работ → матрица требуемых документов`

«Сопровождение» — один внутренний сценарный срез поверх этой матрицы
(раздел 16), не определение системы и не граница готовности. Эта редакция
вводит общее ядро (раздел 5.1–5.5)
перед сценарными агрегатами «Сопровождения» (раздел 5.6 и далее) и меняет
порядок реализации (раздел 17).

### 0.2. Отличия от плана (`DOMAIN_CORE_SPEC_PLAN_v0.1.md`)

План (§2.4) исключал подробную модель МТР/документов и не содержал общего
ядра «Изучение ОКС» вовсе — он был написан для среза «Сопровождение» как
если бы это была вся система. Расхождения зафиксированы как решения
SD-01…SD-05 (раздел 18) и не являются молчаливой заменой плана: план
остаётся историческим основанием для сценарного слоя «Сопровождение», а
общее ядро — новое проектное решение этой редакции.

## 1. Назначение документа

Формально определяет: (а) общее доменное ядро, обязательное для любого
режима АСД-КОНТУР — единый словарь, типы оснований, агрегаты изучения
ОКС и матрицы требуемых документов; (б) внутренний сценарный слой
«Сопровождение» поверх этого ядра — агрегаты исполнения работ,
доказательств и готовности объёма; (в) границы, в которых остальные
режимы (Аудит, Восстановление, Тендер) подключаются к тому же ядру.
Определяет неизменяемые инварианты; команды и условия их выполнения;
доменные события; жизненные циклы; правила версий, происхождения,
подтверждения, отмены и исправления; детерминированные блокирующие
правила; критерии технической завершённости первого внутреннего среза.

По ADR-0007 техническая завершённость такого среза не означает готовности
АСД-КОНТУР: product readiness требует E2E-готовности `Tender`, `Support`,
`Audit` и `Restoration`.

## 2. Статус, основания и границы

### 2.1. Уровни утверждений

- **[ПРОДУКТ]** — утверждённое продуктовое решение;
- **[ADR]** — принятый ADR-0001…0004;
- **[НОРМА]** — нормативный или заданный в задании принцип;
- **[СПЕК]** — проектное решение этой спецификации;
- **[ДОПУЩЕНИЕ]** — требует утверждения владельцем продукта (раздел 18).

### 2.2. Цель первого вертикального среза (исправлено)

**[ПРОДУКТ]** Первый реализуемый срез — не «Сопровождение», а общее
ядро:

`SourceCorpus → StudyOfConstructionObject → WorkTypeRegister → RequirementApplicability → RequiredDocumentMatrix`

Срез должен продемонстрировать: загрузку оснований (всех трёх типов),
вывод перечня видов работ и вывод матрицы требуемых документов (раздел 17).
Полная модель `Source` (версии, конфликты, замещения) и сценарный слой
«Сопровождение» реализуются **после** этого среза (раздел 17).

### 2.3. Входит в срез (общее ядро)

- регистрация `SourceCorpus` — минимального представления версий
  оснований трёх типов (ПД/РД, регламент ИД заказчика, НТД), достаточного
  для запуска изучения, без полной модели версионирования `Source`;
- запуск и проведение `StudyOfConstructionObject`;
- вывод кандидатов `WorkTypeRegister` с происхождением;
- вычисление `RequirementApplicability` по каждому виду работ;
- построение кандидатов `RequiredDocumentMatrix`;
- регистрация `StudyUncertainty` — неопределённостей, требующих
  подтверждения инженером;
- подтверждение инженером кандидатов (виды работ, записи матрицы,
  разрешение неопределённостей) — публикация только после подтверждения
  человеком (раздел 8, граница ИИ/ядра).

### 2.4. Входит в срез (сценарный слой «Сопровождение», после общего ядра)

Как в предыдущей редакции (SD-01): жизненный цикл `MaterialBatch`,
`ControlEvent`, `Defect`, `DocumentDraft`, `Deficit`, `VolumeReadiness`.

### 2.5. Не входит в срез

- конкретный механизм OCR/VLM-извлечения; физическое хранение файлов
  (`TECHNICAL_ARCHITECTURE_v0.1.md` §5); полная генерация содержимого ИД;
  юридически значимое подписание; КС и бухгалтерский учёт; пользовательские
  интерфейсы; конкретная технология транспорта API;
- **(добавлено)** содержательная реализация режимов «Аудит»,
  «Восстановление», «Тендер» сверх границ раздела 16 — они описаны на
  уровне сценария и правил, но их специфичные агрегаты (например, отчёт о
  доказательной дельте для «Аудита») не проектируются в этой редакции;
- юридический анализ договоров и интеграция API smetter.ru
  (`TECHNICAL_ARCHITECTURE_v0.1.md` §10) — зафиксированы, не реализуются.

## 3. Единый язык домена (словарь терминов)

### 3.1. Термины общего ядра (новые/уточнённые в этой редакции)

| Термин | Определение | Происхождение |
|---|---|---|
| Основание (`SourceType`) | Один из различаемых типов документа-опоры: ПД/РД, регламент ИД заказчика, НТД, договор, утверждённый перечень ИД — каждый со своим правилом определения даты применимости | [НОРМА] (задание), `TECHNICAL_ARCHITECTURE_v0.1.md` §4 |
| Корпус оснований (`SourceCorpus`) | Минимальное, но версионируемое представление конкретного набора версий оснований, взятых за основу для одного запуска изучения ОКС | [СПЕК] |
| Изучение ОКС (`StudyOfConstructionObject`) | Процесс-агрегат, поглощающий `SourceCorpus` и производящий кандидатов `WorkTypeRegister`, `RequirementApplicability` и `RequiredDocumentMatrix` | [СПЕК] |
| Неопределённость изучения (`StudyUncertainty`) | Зафиксированный случай, когда изучение не может однозначно распознать вид работы, применимость требования или запись матрицы без решения инженера | [СПЕК], задание п.3 |
| Реестр видов работ (`WorkTypeRegister`) | Перечень распознанных для конкретного ОКС видов работ с устойчивыми идентификаторами, независимыми от нумерации строк НТД | [СПЕК] |
| Матрица требуемых документов (`RequiredDocumentMatrix`) | Соответствие «вид работ → требуемый документ/контроль → основание (требование)» для конкретного ОКС и его текущей ревизии изучения | [СПЕК], задание п.3 |
| Логический источник (`Source`) | Полная, версионируемая идентичность документа-основания независимо от файла — расширение `SourceCorpus` для случаев, требующих истории конфликтов и замещений | [СПЕК], план §5.1 |
| Версия источника (`SourceVersion`) | Неизменяемое опубликованное состояние источника с хешем содержимого и периодом действия | [СПЕК] |
| Локатор фрагмента | Ссылка на конкретное место внутри версии источника — обязательный компонент происхождения | [ADR-0003] |
| Требование (`Requirement`) | Обязательство или критерий, привязанный к версии источника и области применимости | [СПЕК], план §5.2 |
| Применимость требования | Область действия, определяемая **совместно** ПД/РД, договором, утверждённым перечнем ИД, объектом, технологией и датой | [НОРМА] |
| Режим (`ScenarioMode`) | Способ использования уже построенной `RequiredDocumentMatrix`: Сопровождение, Аудит, Восстановление, Тендер — не отдельная копия данных, а набор команд поверх общего ядра | [СПЕК], задание п.4 |

### 3.2. Термины сценарного слоя «Сопровождение» (без изменений)

| Термин | Определение | Происхождение |
|---|---|---|
| Работа/операция (`Work`) | Плановое и фактическое действие с местом, объёмом и связью с актуальной редакцией основания | [СПЕК], план §5.3 |
| Партия МТР (`MaterialBatch`) | Прослеживаемая партия материально-технического ресурса от поставки до места применения | [СПЕК], ФМ §7, §9.2 |
| Контрольная точка (`ControlPoint`) | Условие и обязательный состав доказательств, которые должны существовать до продолжения или сокрытия работ | [СПЕК], план §5.4 |
| Контрольное событие (`ControlEvent`) | Конкретный факт освидетельствования/проверки в рамках контрольной точки | [СПЕК] (SD-02) |
| Доказательство (`Evidence`) | Файл, запись, измерение или иной артефакт, подтверждающий требование или факт | [СПЕК], план §5.5 |
| Дефект (`Defect`) | Зафиксированное несоответствие качества выполненной работы или МТР, выявленное при контрольном событии | [СПЕК] (SD-01), ФМ §7, §11.5 |
| Дефицит (`Deficit`) | Отсутствие, неприемлемость или противоречивость **доказательства** | [СПЕК], план §5.6 |
| Проект документа (`DocumentDraft`) | Отслеживаемое состояние формируемого документа ИД от черновика до архивирования, без логики генерации содержимого | [СПЕК] (SD-01), ФМ §9.5 |
| Готовность объёма (`VolumeReadiness`) | Детерминированно рассчитанный статус доказательной готовности объёма работы к предъявлению | [СПЕК], план §5.7 |
| Происхождение | Обязательная тройка источник + версия + локатор (+ метод и уверенность для машинных полей) | [ADR-0003] |
| Профессиональное решение | Действие уполномоченного человека с зафиксированным основанием, ролью и сроком полномочия | [ПРОДУКТ], план §7.5 |

Отдельно закреплённые различия (без изменений от предыдущей редакции,
плюс одно новое):

- требование не является доказательством;
- доказательство не обязательно является документом;
- наличие файла не означает приемлемость доказательства;
- выполненная работа не равна подтверждённой работе;
- подтверждённая работа не равна готовому к предъявлению объёму;
- синхронизация не означает подтверждение содержания;
- устранённый дефицит не удаляется из истории;
- дефект качества (`Defect`) не равен дефициту доказательства (`Deficit`);
- **(новое)** кандидат `WorkTypeRegister`/`RequiredDocumentMatrix`,
  предложенный изучением, не является опубликованной записью, пока
  инженер не подтвердил его — «распознано» не значит «применимо»
  (раздел 8, граница ИИ/ядра).

## 4. Контекст и граница доменного ядра

### 4.1. Входы общего ядра

`SourceCorpus` трёх типов оснований (раздел 3.1); структура ОКС (вне
объёма этой спецификации — предполагается заданной администратором
объекта, ФМ §14.2); решения инженера по кандидатам изучения; версии
детерминированных правил распознавания и применимости.

### 4.2. Выходы общего ядра

Опубликованный `WorkTypeRegister`; опубликованная `RequirementApplicability`
по каждому виду работ; опубликованная `RequiredDocumentMatrix`; список
неразрешённых `StudyUncertainty`; доменные события для сценарного слоя и
для остальных режимов.

### 4.3. Граница ответственности

Без изменений от плана: ИИ создаёт кандидаты, но не публикует требования
и не устанавливает готовность; ядро проверяет инварианты и рассчитывает
статусы; человек подтверждает профессионально значимые решения; ядро не
выдумывает отсутствующие сведения и не разрешает содержательные конфликты
молча. **[НОРМА]** Уточнение для изучения ОКС: применимость требования не
выводится из присутствия в универсальном нормативном перечне — обязательна
проверка ПД/РД, договора, утверждённого перечня ИД, объекта, технологии и
даты одновременно (раздел 9.1).

## 5. Модель агрегатов

### 5.1. Агрегат «Корпус оснований» (`SourceCorpus`) — новое

**Корень:** `SourceCorpus`. **Сущности:** `SourceCorpus`,
`SourceCorpusEntry` (по одной на каждую включённую версию основания).
**Объекты-значения:** `SourceCorpusId`, `SourceCorpusEntryId`,
`SourceType` (раздел 3.1), `SourceReference` (ссылка на будущую полную
`SourceVersion`, если/когда она заведена — раздел 5.5), `ContentHash`,
`EffectivePeriod`, `AcquisitionProvenance`, `CorpusStatus`.

**Идентификаторы:** `SourceCorpusId` — UUID, один на ОКС и на запуск
изучения; `SourceCorpusEntryId` — UUID на каждую запись.

**Ответственность:** минимально достаточное представление «что взято за
основу» для запуска `StudyOfConstructionObject`, без полной модели
конфликтов/замещений `Source` (которая требуется только когда с
источником начинают работать за пределами разового изучения — раздел 17).

**Инварианты:**

1. Каждая `SourceCorpusEntry` обязана иметь `SourceType`, `ContentHash` и
   `EffectivePeriod` — без исключений ни для одного из трёх обязательных
   типов оснований (раздел 3.1).
2. `SourceCorpus` неизменяем после того, как на его основе запущено
   изучение (`StudyOfConstructionObject` в статусе отличном от
   «черновик») — изменение состава оснований создаёт новый `SourceCorpus`
   и инициирует новый запуск изучения (раздел 11).
3. Отсутствие хотя бы одного обязательного типа основания (ПД/РД,
   регламент ИД заказчика, НТД) не блокирует создание `SourceCorpus`, но
   блокирует переход `StudyOfConstructionObject` в статус, где возможна
   публикация кандидатов матрицы (раздел 10.1) — фиксируется как
   `StudyUncertainty`, не как тихий пропуск.

### 5.2. Агрегат «Изучение ОКС» (`StudyOfConstructionObject`) — новое

**Корень:** `StudyOfConstructionObject`. **Сущности:**
`StudyOfConstructionObject`, `StudyUncertainty`. **Объекты-значения:**
`StudyId`, `StudyRevisionId`, `SourceCorpusRef`, `StudyStatus`,
`RuleSetVersion` (версия правил распознавания/применимости, используемых
при запуске — воспроизводимость, раздел 14).

**Идентификаторы:** `StudyId` — UUID, стабилен для ОКС;
`StudyRevisionId` — UUID, новый при каждом перезапуске (раздел 11).

**Ответственность:** оркестрация процесса изучения; накопление
кандидатов (делегируется `WorkTypeRegister`, `Requirement`,
`RequiredDocumentMatrix`, каждый из которых публикует собственные
кандидаты по собственным правилам — `StudyOfConstructionObject` не
дублирует их инварианты, а координирует последовательность и завершение);
регистрация `StudyUncertainty`, когда распознавание не может дать
однозначный кандидат.

**Инварианты:**

1. `StudyOfConstructionObject` не может быть завершено (`StudyStatus =
   завершено`), пока существует хотя бы одна неразрешённая
   `StudyUncertainty`, помеченная как блокирующая (раздел 10.1).
2. Каждый кандидат, опубликованный в рамках изучения, обязан ссылаться на
   `StudyId`/`StudyRevisionId` и `RuleSetVersion` — воспроизводимость
   вывода (раздел 14).
3. Повторный запуск после изменения `SourceCorpus` создаёт новую
   `StudyRevisionId`; предыдущая ревизия и её опубликованные кандидаты не
   удаляются (раздел 11).

### 5.3. Агрегат «Реестр видов работ» (`WorkTypeRegister`) — новое

**Корень:** `WorkTypeRegister`. **Сущности:** `WorkTypeRegister`,
`WorkTypeEntry`. **Объекты-значения:** `WorkTypeId`, `WorkTypeLabel`,
`RegulatoryRowReference` (номер строки приложения А/Б СП 543 конкретной
`SourceVersion`/`SourceCorpusEntry` — аннотация, не идентификатор),
`RecognitionProvenance` (источник, локатор, метод, уверенность),
`WorkTypeEntryStatus` (`кандидат / подтверждён / отклонён`).

**Идентификаторы:** `WorkTypeId` — UUID, присваивается при первом
распознавании, **не зависит и не выводится** из номера строки НТД
(раздел 9.1, [НОРМА] — прямое требование задания, дословно перенесено из
предыдущей редакции без изменений).

**Ответственность:** перечень распознанных для конкретного ОКС видов
работ с происхождением; разграничение кандидата и подтверждённой записи.

**Инварианты:**

1. `WorkTypeEntry` в статусе «кандидат» не может использоваться как
   основание для публикации `RequiredDocumentMatrix` (раздел 8) —
   только «подтверждён».
2. Смена редакции СП 543 (новая `SourceVersion` с новой нумерацией строк)
   не меняет `WorkTypeId` уже подтверждённых записей — обновляется только
   `RegulatoryRowReference`, создаётся событие проверки влияния (по
   аналогии с ФМ §11.2 для устаревшей РД).
3. Отклонённая инженером запись сохраняется в истории со статусом
   «отклонён», не удаляется (симметрично инвариантам версий, раздел 12).

### 5.4. Агрегат «Требование» (`Requirement`)

Без изменений от предыдущей редакции. **Корень:** `Requirement`.
**Сущности:** `Requirement`, `RequirementRevision`,
`RequirementApplicability`, при необходимости `RequirementConflict`.

**[НОРМА]** `RequirementApplicability` — составное поле, обязаны быть
заполнены (или явно отмечены как неприменимые с основанием) все из:
`ProjectDocScope` (ПД/РД), `ContractScope` (договор), `ApprovedListScope`
(утверждённый перечень ИД), `ObjectScope` (объект/зона),
`TechnologyScope` (технология выполнения), `ValidityPeriod` (дата).
Требование не может считаться применимым по умолчанию только из
присутствия в универсальном нормативном перечне.

**Инвариант о переходных положениях [НОРМА]:** несоответствие устаревшей
форме или редакции документа не создаётся автоматически без проверки
`EffectivePeriod` источника и без проверки наличия переходных положений
в тексте источника (локатор обязателен для такого вывода).

### 5.5. Агрегат «Матрица требуемых документов» (`RequiredDocumentMatrix`) — новое

**Корень:** `RequiredDocumentMatrix`. **Сущности:**
`RequiredDocumentMatrix`, `RequiredDocumentMatrixEntry`.
**Объекты-значения:** `MatrixId`, `MatrixRevisionId`, `WorkTypeRef`
(ссылка на подтверждённый `WorkTypeEntry`), `RequiredDocumentKind`
(вид обязательного документа/контроля), `ControlKind`, `BasisRequirementRef`
(ссылка на `Requirement`, которым обосновано требование), `EntryStatus`
(`кандидат / подтверждена / отклонена / устарела`).

**Идентификаторы:** `MatrixId` — UUID, один на ОКС; `MatrixRevisionId`
— UUID на каждую ревизию (раздел 11); `RequiredDocumentMatrixEntry` —
собственный UUID на каждую строку.

**Ответственность:** финальный, подтверждаемый инженером результат
изучения — единственный источник ответа на вопрос «какой документ/
контроль обязателен для этого вида работ и на каком основании» для всех
режимов (раздел 16).

**Инварианты:**

1. Каждая `RequiredDocumentMatrixEntry` обязана ссылаться и на
   подтверждённый `WorkTypeEntry`, и на опубликованный `Requirement` —
   запись без обоих оснований не может иметь статус «подтверждена».
2. Матрица без единого пропуска не публикуется автоматически «полной» —
   отсутствие записи для распознанного вида работ фиксируется как
   `StudyUncertainty`, не как молчаливое отсутствие требований.
3. Изменение основания (`Requirement` заменён/отозван, раздел 12)
   инициирует пересмотр зависимых записей матрицы новой ревизией, не
   переписывает прежнюю (раздел 11).
4. Публикация записи как «подтверждена» — исключительно действие
   человека (раздел 8) — ИИ не публикует записи матрицы напрямую.

### 5.6. Агрегат «Источник» (`Source`) — полная модель, реализуется последним

Без изменений от предыдущей редакции (план §5.1). **Корень:** `Source`.
**Сущности:** `Source`, `SourceVersion`, `SourceApplicabilityDecision`.
Расширяет `SourceCorpus` (раздел 5.1) полной историей версий, конфликтов

матрицы: повторные редакции, конфликтующие источники, отзыв. Порядок
реализации — раздел 17.

## 6. Связи между агрегатами

```text
SourceCorpus (три раздельных SourceType: ПД/РД, регламент ИД заказчика, НТД, +Договор/Перечень ИД)
 └─ StudyOfConstructionObject
      ├─ StudyUncertainty (неопределённости → инженеру)
      ├─→ WorkTypeRegister ──(WorkTypeEntry, RegulatoryRowReference — не ID)
      ├─→ Requirement ── RequirementApplicability (6 измерений применимости)
      └─→ RequiredDocumentMatrix ──(WorkTypeRef + BasisRequirementRef)

Source (полная модель, расширяет SourceCorpus, реализуется последним)

──────────────────── сценарный слой «Сопровождение» ────────────────────

RequiredDocumentMatrix
      ├─ WorkRequirementLink ── Work ── WorkVolume
      │                          └─ WorkType (= WorkTypeId из WorkTypeRegister)
      └─ EvidenceRequirement ── ControlPoint
                                 └─ ControlEvent
                                      ├─ Evidence
                                      ├─ Defect (дефект качества)
                                      └─ Deficit (дефицит доказательства)

MaterialBatch ── ApplicationRecord ── Work
              └─ QualityDocument (вид Evidence)
              └─ IncomingControlDecision

DocumentDraft ── SubjectWork (Work)
              └─ RequiredEvidenceSet (Evidence)
              └─ DocumentKind ← RequiredDocumentMatrixEntry

WorkVolume + ControlPoint + Defect + Deficit
                 └─ VolumeReadiness
```

Ключевые правила (нумерация продолжает предыдущую редакцию, п.1–11 без
изменений по существу, добавлены п.12–14):

12. `StudyOfConstructionObject` не связывается с `Work` напрямую —
    единственная точка сцепления общего ядра и сценарного слоя —
    `RequiredDocumentMatrix` (раздел 5.5), что позволяет остальным
    режимам (раздел 16) подключаться к тому же ядру без модели `Work`.
13. `WorkTypeId` — единственный устойчивый идентификатор вида работы во
    всей системе; `Work.WorkType`, `RequiredDocumentMatrixEntry.WorkTypeRef`
    и любые будущие ссылки (Аудит, Тендер) обязаны использовать его, а не
    вводить параллельную классификацию.
14. `Source` (полная модель) не заменяет `SourceCorpus` — `SourceCorpus`
    продолжает существовать как снимок, на основе которого была запущена
    конкретная ревизия изучения, даже после того, как для отдельных
    оснований заведена полная история `Source`.

## 10. Переходы состояний

### 10.1. StudyOfConstructionObject — новое

```text
черновик → сбор корпуса → изучается → есть неразрешённые неопределённости
                                     ├→ завершено
                                     └→ прервано
```

Переход «завершено» невозможен при наличии блокирующей
`StudyUncertainty` (раздел 5.2, инвариант 1). Повторный запуск после
изменения `SourceCorpus` — новая ревизия, не новый статус того же
объекта (раздел 11).

### 10.2. WorkTypeEntry (в составе WorkTypeRegister) — новое

```text
распознан (кандидат) → проверяется инженером → подтверждён
                                              └→ отклонён
```

Подтверждённая запись при смене редакции НТД получает событие проверки
влияния, не переходит автоматически ни в «отклонён», ни в «требует
пересмотра» без решения человека.

### 10.3. RequiredDocumentMatrixEntry — новое

```text
кандидат (от изучения) → проверяется инженером → подтверждена
                                                 ├→ отклонена
                                                 └→ устарела (при отзыве основания)
```

### 10.4. Source, Requirement, Work, MaterialBatch, Evidence, ControlPoint/ControlEvent, Defect, Deficit, DocumentDraft, VolumeReadiness

Без изменений от предыдущей редакции — переносятся дословно (разделы
10.1–10.10 прежней нумерации). Не дублируются здесь во избежание
рассинхронизации; см. историю документа при необходимости точной сверки
(файл версионируется в git).

## 16. Режимы как подключаемые сценарии

### 16.1. Принцип

Ни один режим не содержит собственной копии «Изучения ОКС» — все читают
одну и ту же `RequiredDocumentMatrix` (раздел 5.5) для данного ОКС.
Различие режимов — исключительно в командах и агрегатах, которые каждый
режим добавляет **поверх** общего ядра, не в способе получения перечня
видов работ или требуемых документов.

### 16.2. Сопровождение (внутренний Support-срез)

Добавляет сценарный слой раздела 5.7–5.14: `Work`, `MaterialBatch`,
`ControlPoint`/`ControlEvent`, `Evidence`, `Defect`, `Deficit`,
`DocumentDraft`, `VolumeReadiness`. Единственный режим, чьи агрегаты
специфицированы в этой редакции до уровня команд/событий/состояний.

### 16.3. Восстановление ИД (обязательный режим; не специфицирован полностью в этой редакции)

**[ПРОДУКТ]** Явное разграничение, требуемое заданием:

- **Допустимо.** `DocumentDraft` формируется из уже существующих
  подтверждённых `Evidence` — включая доказательства, полученные не в
  реальном времени стройки, а при последующем обследовании (архивные
  сканы, натурные измерения, свидетельские показания, зафиксированные
  как `Evidence` со своим происхождением и `EvidenceVerification`). Режим
  меняет **источник получения** доказательства, не отменяет требование
  «доказательство обязательно и подтверждено» (раздел 7, план §7.5).
- **Недопустимо.** `DocumentDraft` или `Evidence`, для которых нет
  ссылки на подтверждённый источник — правдоподобно сгенерированные
  дата, подпись, результат испытания или факт присутствия лица. Ядро не
  предоставляет для «Восстановления» отдельного, более мягкого пути
  публикации `DocumentDraft` в обход `EvidenceVerification` (раздел 5.9)
  — команда `MarkDraftReadyForSignature` (раздел 8, план §8.11) отклоняется
  при отсутствии подтверждённого `RequiredEvidenceSet`, независимо от
  режима, инициировавшего команду.
- Агрегат для доказательной дельты «Восстановления» (что фактически
  отсутствует относительно матрицы) не специфицирован в этой редакции —
  зафиксирован как открытое решение (раздел 18).

### 16.4. Аудит (обязательный режим; не специфицирован полностью в этой редакции)

Сравнивает `RequiredDocumentMatrix` с фактическим корпусом
`Evidence`/`DocumentDraft` для уже выполненных работ; вычисляет дельту.
Не создаёт `Work`/`MaterialBatch` — режим только для чтения относительно
сценарного слоя «Сопровождение», с одним исключением на запись —
собственный отчёт о дельте (тип и агрегат не специфицированы, раздел 18).

### 16.5. Тендер (обязательный режим; не специфицирован полностью в этой редакции)

Использует `RequiredDocumentMatrix` для оценки объёма обязательной
доказательной базы до заключения договора. Зависит от смежных
перспективных модулей (раздел 17 `TECHNICAL_ARCHITECTURE_v0.1.md`) —
юридического анализа договора и сметной оценки. Не специфицируется в
этой редакции.

## 17. Порядок реализации и критерии технической завершённости первого среза

### 17.1. Порядок (по прямому указанию)

```text
SourceCorpus/StudyOfConstructionObject → WorkTypeRegister
    → RequirementApplicability → RequiredDocumentMatrix → Source (полная модель)
```

`Source` (раздел 5.6) — единственный агрегат общего ядра, реализуемый
**последним**, а не первым, как в предыдущей редакции. Причина: первый
срез должен показать сквозную цепочку «загрузка оснований → вывод видов
работ → вывод матрицы» на минимальном представлении оснований
(`SourceCorpus`), не требуя одновременно полной модели версионирования,
конфликтов и замещений источника — эта полнота нужна только когда с
источником начинают работать за пределами разового изучения (повторные
редакции РД по ходу стройки, конфликтующие источники — сценарный слой
«Сопровождение» и последующие режимы).

### 17.2. Критерии технической завершённости первого среза

Проверяемый чек-лист. Реализация модулей `source_corpus`, `study`,
`work_type_register`, `requirement`, `required_document_matrix`
(`TECHNICAL_ARCHITECTURE_v0.1.md` §3.1) может начинаться, когда выполнено
всё нижеперечисленное:

| № | Критерий | Статус на дату документа |
|---|---|---|
| 1 | Словарь терминов общего ядра зафиксирован (раздел 3.1) | выполнено |
| 2 | Идентификаторы определены для всех пяти агрегатов среза (разделы 5.1–5.5) | выполнено |
| 3 | Инварианты зафиксированы и не зависят от нерешённых SD/D пунктов, блокирующих только сценарный слой | выполнено — инварианты §5.1–5.5 не ссылаются на SD-01 (расширение на МТР), SD-02 (ControlEvent), SD-03 (отступление для Defect) |
| 4 | Состояния и переходы определены для `StudyOfConstructionObject`, `WorkTypeEntry`, `RequiredDocumentMatrixEntry` (раздел 10.1–10.3) | выполнено |
| 5 | Команды и события определены (раздел 8.1, 9.1) | выполнено |
| 6 | Правило происхождения и темпоральной применимости определено для всех трёх типов оснований (раздел 7.1) | выполнено |
| 7 | Хранение не требует выбора конкретной СУБД для написания домена (порт, не адаптер) | выполнено — `TECHNICAL_ARCHITECTURE_v0.1.md` §3, домен не зависит от AD-01 |
| 8 | Гранулярность `SourceCorpus`/`StudyOfConstructionObject` (AD-05/SD-04) | **не выполнено — требует утверждения**, но не блокирует написание кода при выборе рекомендации (два агрегата) как рабочей гипотезы |
| 9 | Тестовая стратегия для агрегатов среза определена | выполнено — `TECHNICAL_ARCHITECTURE_v0.1.md` §12 |
| 10 | Матрица трассировки для общего ядра заполнена (раздел 15) | выполнено (фрагмент) |
| 11 | Владелец продукта утвердил оба документа | **не выполнено — требуется утверждение** |

**Вывод:** доменная модель общего ядра (`SourceCorpus`,
`StudyOfConstructionObject`, `WorkTypeRegister`, `Requirement`,
`RequiredDocumentMatrix`) технически полна для начала реализации без
персистентности и без сценарного слоя «Сопровождение». Блокирующие
позиции — формальное утверждение (строка 11) и рекомендация по AD-05/
SD-04 как рабочая гипотеза, а не обязательное предварительное решение
(строка 8). Полная модель `Source` (раздел 5.6) реализуется после
подтверждения, что цепочка среза работает на минимальном представлении
оснований.

## 18. Решения, требующие утверждения владельца продукта

### 18.1. Перенесённые из плана без изменений

Единица готовности; граница агрегата готовности; связь требования и
контрольной точки; повторное использование доказательства; допустимое
исключение для дефицита; статус при нормативной коллизии; отзыв
основания и историческая готовность; публикация требования; закрытие
контрольной точки с условием; неустранимый дефицит. Формулировки — см.
`docs/mvp/DOMAIN_CORE_SPEC_PLAN_v0.1.md` §16.1.

### 18.2. Перенесённые из предыдущей редакции (уточнены)

- **SD-01 — Расширение среза на МТР/дефект/проект документа** (сценарный
  слой «Сопровождение», реализуется после общего ядра — раздел 17.1).
- **SD-02 — Разделение `ControlPoint`/`ControlEvent`.**
- **SD-03 — Допустимое согласованное отступление для `Defect`.**

### 18.3. Новые в этой редакции

- **SD-04 / AD-05 — Гранулярность `SourceCorpus` и
  `StudyOfConstructionObject`.** Один агрегат или два (раздел 5.1–5.2).
  Решение единое с `TECHNICAL_ARCHITECTURE_v0.1.md` §13.5.
- **SD-05 — Модель повторного запуска изучения.** Требует решить: должен
  ли `RerunStudyOfConstructionObject` выполняться автоматически при любом
  изменении `SourceCorpus`, или только по явной команде инженера
  (раздел 11.1, п.1 сейчас предполагает только предложение кандидата
  действия, не автозапуск — рабочая гипотеза, не решённый вопрос).
- **SD-06 — Агрегат отчёта о доказательной дельте («Аудит»).** Не
  специфицирован в этой редакции (раздел 16.4) — нужен отдельный проход
  по режиму «Аудит», выходящий за рамки текущего задания.
- **D-02 — Пилотный ОКС и технологическая цепочка** (исправлено, единым
  пунктом, как в `FUNCTIONAL_MODEL_v0.1.md` §22 — см.
  `TECHNICAL_ARCHITECTURE_v0.1.md` §13.6).
- **D-04 — Первая организационная модель использования** (исправлено, как
  в `FUNCTIONAL_MODEL_v0.1.md` §22 — не путать с технологической цепочкой,
  ошибочно приписанной этому номеру в предыдущей редакции).

Открытые решения не блокируют реализацию общего ядра (раздел 17.2) — они
блокируют сценарный слой «Сопровождение» (SD-01–03), режимы «Аудит»/
«Восстановление» (SD-06, раздел 16.3–16.4) и наполнение реальными
пилотными данными (D-02, D-04).
